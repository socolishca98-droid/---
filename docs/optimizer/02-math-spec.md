# Этап 2. Математическая спецификация оптимизатора

Дата: 1 ноября 2026. Статус: **на утверждение**. Реализация не начата.

Обозначения: `N` — заказы организации, `V` — её машины, `0` — база машины.
Все величины — в одной валюте (₽) и без НДС, если не сказано иное.

---

## 1. Входные данные

### 1.1. Организация (tenant)

```
Organisation = {
  id, timezone, currency, vatMode,             // 'included' | 'excluded' | 'mixed'
  basePlaces: Place[],                          // одна или несколько баз
  settings: Settings,
  regionParams: RegionParams[]                  // настраиваемые, не в коде
}
```

Изоляция: **любой** вход движка обязан содержать `organisationId`, и все
заказы/машины/настройки берутся только по нему. Движки не читают базу сами —
им передают данные; это делает изоляцию проверяемой на уровне контракта.

### 1.2. Заказ (load)

```
Load = {
  id, organisationId,
  pickup:  Place, delivery: Place,
  weightKg, volumeM3, bodyRequired: BodyClass[],   // требования фрахтователя
  window: { pickupFrom?, pickupTo?, deliveryFrom?, deliveryTo? },  // местное время точек
  rate: { amount, basis: 'trip' | 'perKm' | 'perTon' | 'perHour', vatIncluded },
  source: 'exchange' | 'board', externalId
}
```

`window` может быть неполным: `from` без `to` (открытое окно), обе пустые
(дата неизвестна → считается доступным с момента `now`). Любая неполнота
попадает в `assumptions` маршрута (см. § 9).

### 1.3. Машина (vehicle)

```
Vehicle = {
  id, organisationId, plate,
  homeBase: Place,                          // база МАШИНЫ (по умолчанию — база орг.)
  capacityKg, capacityM3,
  body: BodyClass[],                        // что реально можно грузить
  consumption: { lPer100, byLoad?: fn },     // расход топлива
  costs: CostProfile,                        // см. § 8
  status: 'available' | 'in_use' | 'maintenance',
  driver?: { id, shiftHours, payRule }
}
```

### 1.4. Параметры (настройки, а не константы кода)

| Группа | Параметр | Смысл | Предлагаемое значение по умолчанию |
| --- | --- | --- | --- |
| `Settings` | `returnMode` | `required` / `preferred` / `free` | `preferred` |
| | `minContributionPerKm` | порог экономики **цепочки** | 0 (не фильтр), показывается предупреждением |
| | `maxRouteHours` | лимит календарного времени | 72 |
| | `maxLegs` | предел плеч | 12 |
| | `detourBaseKm` | «по пути» | задаётся как доля маршрута, см. § 4.6 |
| | `drivingLimitHours` | норма вождения между отдыхами | 9 |
| | `restHours` | отдых | 11 |
| | `handlingHours` | функция от массы/типа | 1ч/1000 кг, минимум 1,5 |
| `RegionParams` | `speedLoadedKmh` | скорость с грузом | по региону |
| | `speedEmptyKmh` | порожним | по региону |
| | `roadFactor` | оценка дороги от прямой | по региону, с пометкой |
| | `tollSegments` | платные участки | по данным |

## 2. Переменные решения

Для машины `v` и подмножества заказов `S ⊆ N`:

- `x_{i,j} ∈ {0,1}` — переход между точками `i` и `j` (точки: база, погрузки,
  выгрузки); `i,j ∈ P ∪ D ∪ {0}`;
- `q_{i}` — масса в кузове на участке `i`;
- `vol_{i}` — объём в кузове на участке `i`;
- `t_{i}` — момент времени (UTC) прибытия в точку `i`;
- `w_{i}` — ожидание в точке `i`;
- `y_{k} ∈ {0,1}` — заказ `k` взят;
- `r ∈ {0,1}` — машина возвращается на базу.

Модель А — частный случай, где для каждого участка `|заказов в кузове| ≤ 1`.

---

## 3. Жёсткие ограничения

1. **Поток.** Каждая точка посещается не более одного раза; маршрут начинается
   в базе и заканчивается либо в базе (`r = 1`), либо в последней выгрузке.
2. **Вместимость (для каждого участка между последовательными событиями):**
   `q_i ≤ capacityKg` и `vol_i ≤ capacityM3`. Проверяется по профилю, а не «по
   грузу».
3. **Кузов.** `bodyRequired ⊆ body(vehicle)`; иначе заказ несовместим
   (совместимость — отдельный движок, причина возвращается словами).
4. **Время:**
   - `t_{pickup, k} ≥ t_arrival + w`, `w ≥ 0`;
   - погрузка не раньше `window.pickupFrom` (местное → UTC);
   - `t_{delivery, k} ≥ t_{pickup, k} + handling_hours(k) + travel`;
   - выгрузка внутри `window.delivery` (если окно задано);
   - **груз нельзя доставить раньше его погрузки** — прямое следствие
     предыдущего; отдельное ограничение только в отчёте о нарушении.
5. **Режим труда:** суммарное вождение между отдыхами ≤ `drivingLimitHours`;
   после — отдых ≥ `restHours`. Отдых входит в календарное время.
6. **Лимит календарного времени:** `t_end − t_start ≤ maxRouteHours`
   (считается по календарю, включая ожидания и отдых).
7. **Возврат (режим `required`):** `r = 1` строго. В режимах `preferred` и
   `free` — не ограничение, а составляющая цели (§ 7).
8. **Согласованные заказы:** `y_k = 1` для `k ∈ keepIds`; если цепочка с ними
   невозможна, это не «нет маршрута», а **отчёт о невозможности** с указанием,
   какой заказ и какое ограничение мешает (отдельный результат, не пустой экран).

## 4. Целевая функция

### 4.1. Базовая

`F(chain) = Σ доход(k) − [ топливо + оплата водителя + износ/ТО + шины +
платные дороги + прочие переменные + постоянные, относимые на рейс ]`

где каждый компонент считается **из своей базы и ровно один раз** (§ 8).

### 4.2. Что не входит в F (чтобы не было двойного вычета)

- порожний пробег входит **только через** топливо и километровые статьи;
- «ставка работы машины ₽/км» — это **не отдельная статья**, а сумма
  километровых статей; нельзя вычитать и её, и её составляющие;
- оплата водителя — либо по часам, либо за смену, **не** одновременно с
  километровой ставкой, в которую она уже вложена.

### 4.3. Компоненты по умолчанию (настраиваются)

| Статья | Формула по умолчанию | Основание |
| --- | --- | --- |
| Топливо | `Σ сегментов: (км / 100) × lPer100 × цена_л_регион` | расход из карточки; нет — оценка с флагом |
| Водитель | `Σ смен × ставка_смены` (норма 9 ч) | смены считает Time Engine |
| Износ/ТО | `₽/км × пробег` | настройка организации |
| Шины | `₽/км × пробег` | настройка |
| Платные дороги | по сегментам из `tollSegments` | иначе `null` + пометка |
| Прочие | `₽/км` | настройка |
| Постоянные | `₽/сутки × дни_рейса`, отдельной строкой | не вычитается из «остаётся», показывается как покрытие |

### 4.4. Дополнительные показатели (в отчёте, не в F)

`netPerKm`, `netPerHour`, `emptyShare`, `loadedKm`, `emptyKm`,
`fixedContribution`, `confidence`.

### 4.5. Возврат на базу (три режима)

- `required`: маршрут без выхода в базу **недопустим**; поиск ищет лучший из
  замкнутых.
- `preferred`: возврат не обязателен; сравниваются варианты:
  `(a)` вернуться порожним, `(b)` вернуться с грузом, `(c)` не возвращаться.
  Выбор — по `F` с учётом **стоимости возврата**: возврат порожним уменьшает
  `F` на топливо и километровые статьи возврата; возврат с грузом — увеличивает
  `F` на доход обратки.
- `free`: конечная точка не важна; возврат не добавляется в маршрут, но в
  отчёте показывается, во что он обошёлся бы.

**Ключевое отличие от текущего поведения:** режим возврата участвует в
поиске, а не проверяется после. Для `preferred` в DP добавляется состояние
«мы ещё не решили, вернёмся или нет», и решение принимается по цепочке целиком.

### 4.6. Отклонение «по пути»

`detour(v) = max(detourBaseKm, α × длина_маршрута_к_текущей_точке)`,
α ≈ 0,15. Это делает правило масштабируемым: 150 км для рейса на 400 км и для
рейса на 3 000 км — разные величины.

## 5. Критерии ранжирования (несколько вариантов, а не один)

Оптимизатор возвращает **K лучших различных цепочек** (по умолчанию 3–5) и
рекомендацию. Варианты ранжируются по выбранному пользователем критерию:

| Критерий | Ключ сортировки | Когда нужен |
| --- | --- | --- |
| Максимальная прибыль | `F` | «заработать за рейс» |
| Прибыль на километр | `F / totalKm` | «не гонять машину зря» |
| Минимум порожнего пробега | `emptyShare ↑` при `F ≥ 0,9·Fmax` | «не уводи далеко» |
| Минимальная продолжительность | `totalHours` при `F ≥ 0,9·Fmax` | «нужна машина на базе» |
| Обязательный возврат | фильтр `r = 1`, затем `F` | «машина должна быть дома» |

Правило: критерии «порожний пробег» и «продолжительность» **не отбрасывают**
более денежный вариант, а показывают его рядом — логист решает сам, видя оба
числа. Порог 35 % порожняка как отсечка **отменяется**: он остаётся
предупреждением.

Детерминизм: при равенстве `F` — сортировка по `(totalHours, id цепочки)`,
чтобы результат не «прыгал» между запусками.

## 6. Постановка для двух моделей

### 6.1. Модель А — последовательные перевозки

Дополнительное ограничение: на любом участке в кузове ≤ 1 заказ.
Формально это ужесточение § 3.2 до `|{k ∈ S : pickup_k ≤ i < delivery_k}| ≤ 1`.

Точное решение: DP по `(S, last_k, time, driveSinceRest)` с доминированием.
Критерий доминирования:

> метка `A` вытесняет `B`, если `S_A = S_B`, `last_A = last_B`, `t_A ≤ t_B`,
> `driveSinceRest_A ≤ driveSinceRest_B` и `F_A ≥ F_B`.

Сложность — экспоненциальная по числу заказов, поэтому:
- при `|N| ≤ 14` — **точный оптимум** (проверяется перебором в тестах);
- при `|N| > 14` — DP с отсечением по верхней оценке (A\*): `F + Σ лучших
  оставшихся ставок` как `h`. Потери относительно точного оптимума на
  подвыборке измеряются отдельно и попадают в протокол (§ 10).

### 6.2. Модель Б — сборные перевозки

Один заказ на плече снимается, вместо этого:

- подмножество заказов `S` совместимо, если существует такая
  последовательность погрузок и выгрузок `π`, что на каждом участке
  `Σ вес ≤ capacityKg`, `Σ объём ≤ capacityM3`;
- груз не может быть выгружен раньше своей погрузки (естественный порядок
  pickup_k → delivery_k);
- временные окна соблюдены для обеих точек каждого заказа.

Проверка: для данного `π` — линейный проход по профилю (Capacity Engine).
Поиск: перебор `π` для `|S| ≤ 6` заказов (12 точек — до 12! слишком много,
поэтому: перебор подмножеств × перестановок погрузок с достройкой выгрузок по
правилу «ближайшая возможная», плюс ветвление по порядку), иначе — эвристика
с обязательной проверкой профиля.

### 6.3. Сравнение моделей

Обе решаются на одном пуле; для каждой машины берётся лучшая цепочка каждой
модели; победитель — по `F` (с учётом выбранного критерия). На экране —
пометка модели и разница в деньгах: «сборный вариант: +12 400 ₽, на 4 ч
дольше».

## 7. Время: формальное расписание

События маршрута: `depart(base) → arrive(pickup_k) → wait → load → depart →
arrive(delivery_k) → wait → unload → … → arrive(base)`.

```
travel(i→j) = km(i→j) / speed(mode, region(i,j)) + breaks(travel)
handling(k) = f(weightKg_k, body, region)     // настраиваемая функция
t_depart    = max(now + preparation, openingPolicy)   // «выезд не в 23:00»
```

Правила:

- все времена хранятся в UTC; в интерфейсе показываются в **местном времени
  точки** (`Place.timezone`, IANA);
- переход через часовой пояс — событие таймлайна с указанием сдвига;
- ожидание окна и ожидание «следующего заказа» — разные статьи отчёта;
- если данных недостаточно (нет окна, нет координат) — `confidence`
  понижается, а в `assumptions` пишется, что именно неизвестно.

## 8. Экономика без двойного учёта

Правило единственного владельца статьи:

```
доход            — только из rate
топливо          — только из consumption × км × цена
водитель         — только из payRule (смены/часы), НЕ из ₽/км
износ, ТО, шины  — только из ₽/км
платные дороги   — только из tollSegments
прочие           — только из ₽/км
постоянные       — только как «покрытие», не вычитаются из остатка
```

Проверка в тестах: для заданных настроек `Σ статей` совпадает с независимым
пересчётом до рубля; ни одна статья не входит дважды (проверяется тестом
«убери статью — сумма изменится ровно на неё»).

НДС: доход приводится к базе расчёта (`vatMode`), расходы — к той же базе;
если режим смешанный — в `vatNote` пишется, что именно не приведено.

## 9. Достоверность

```
confidence: 'measured' | 'estimated' | 'assumed'
assumptions: string[]   // человеческим языком
```

Правила:

- расстояние из маршрутизатора — `measured`; из биржи — `measured` (километраж
  ATI); из `haversine × factor` — `estimated`;
- расход топлива из карточки — `measured`, типовой — `estimated`;
- нет окна выгрузки — `assumed` («время выгрузки не задано»);
- нет ставки водителя — `assumed` («взята ставка организации»).

Маршрут с `assumed` в решающих параметрах помечается на экране, а не только в
логе.

## 10. Критерии приёмки (Этап 6)

1. **Допустимость.** Ни один выданный маршрут не нарушает § 3 (проверяется
   независимым валидатором на всех сценариях и на случайных задачах).
2. **Оптимальность на малых.** Для `|N| ≤ 12` результат равен полному
   перебору по `F` (допуск 0,1 % — на округлениях).
3. **Качество на средних.** Для `14 < |N| ≤ 40` — не хуже эталона (перебор с
   отсечением / MILP) более чем на 1 %.
4. **Географическая нейтральность.** Тесты с базами Ярославль, Москва,
   Екатеринбург, Краснодар, Владивосток (5 часовых поясов) — одинаковое
   качество; ни одной координаты в коде.
5. **Изоляция.** Сценарий с двумя организациями: заказы и машины одной не
   появляются в результате другой ни при каких настройках.
6. **Экономика.** Ни одной статьи дважды; сумма сходится с ручным расчётом.
7. **Производительность.** Пул 200 заказов, 10 машин, лимит 72 ч:
   ≤ 2 с на машину в среднем, ≤ 10 с худший случай, с замером числа
   рассмотренных и отсечённых состояний.
8. **Прозрачность.** Для каждого маршрута есть: последовательность, плечи с
   километрами, календарь, экономика по статьям, возврат, предупреждения,
   `confidence`/`assumptions`.

## 11. Зафиксированные решения (1 ноября, ответы заказчика)

| Вопрос | Решение | Следствие для спецификации |
| --- | --- | --- |
| Расстояния | **Свой OSRM** | Distance Engine — обёртка над OSRM с кешем и явной пометкой `estimate` при отказе |
| Сборные перевозки | **Сразу после модели А** | Этап 4 делится на 4a (А, точно) и 4b (Б, тем же контрактом) |
| Оплата водителя | **Правила у каждой организации свои** | `payRule` — полиморфный и настраиваемый; калькулятор поддерживает все базы, а не одну |
| Где считать | **На сервере (API)** | Сборка переезжает из браузера в API; экран получает готовые варианты и протокол |

### 11.1. Distance Engine на OSRM

```
Segment = {
  km, hours,
  source: 'osrm' | 'exchange' | 'estimate',
  confidence: 'measured' | 'estimated',
  tollsRub: number | null,
  profile: 'car' | 'truck'
}
```

Правила:

- профиль `truck` с габаритами машины (высота, масса, оси) — если OSRM
  развёрнут с truck-профилем; иначе `car` + поправка на скорость и **пометка**;
- кеш по паре `(fromId, toId, profile)`: одна и та же пара не считается дважды
  ни внутри запуска, ни между запусками (таблица/Redis, ключ — стабильные id
  точек, а не строка адреса);
- отказ OSRM → `estimate` (прямая × `roadFactor` региона) с понижением
  `confidence`; маршрут с оценкой помечается на экране, а не только в логе;
- километраж ATI по грузу (`distanceKm`) считается `measured` и имеет
  приоритет над OSRM для этого плеча: это то расстояние, по которому
  фрахтователь считает ставку.

### 11.2. Оплата водителя: правила организации

`CostProfile.payRule` — один из вариантов, настраивается по организации (и при
необходимости переопределяется у машины):

| `payRule` | Формула | Когда применяют |
| --- | --- | --- |
| `perShift` | `ставка_смены × число_смен` | большинство перевозчиков; простой становится расходом |
| `perKm` | `₽/км × пробег` | сдельная оплата |
| `perHour` | `₽/час × часы_работы` (движение + погрузка + ожидание) | неравномерная загрузка |
| `perTrip` | фиксированная сумма за рейс | короткие рейсы |
| `mixed` | `оклад + премия_₽/км` | комбинированная схема |

Правило единственного владельца статьи сохраняется: если выбрано `perShift`,
`₽/км` в `CostProfile` **не должен** содержать оплату водителя — это
проверяется тестом «убери статью, сумма изменится ровно на неё». Смена
считается Time Engine по норме вождения организации (§ 7), а не «как получится».

### 11.3. Серверный расчёт

- API `POST /api/logist/routing/plan`: вход — `organisationId`, `vehicleIds`,
  параметры запуска; выход — варианты маршрутов + протокол решения
  (число состояний, отсечения, время, разрыв с эталоном на малых пулах).
- Экран только отображает: логика выбора не дублируется в браузере.
- Идемпотентность: один и тот же вход (пул, настройки, `now`) даёт один и тот
  же маршрут — это проверяется тестом.
- Долгие расчёты — задача с прогрессом; лимит времени на запуск, при
  превышении возвращается лучший найденный вариант с пометкой «не доведён до
  оптимума».

## 12. Изменения относительно спецификации, принятые при реализации

Реализация ядра (`lib/routing/`) уточнила три места спецификации. Изменения не
косметические, поэтому зафиксированы здесь, а не «как получилось».

### 12.1. Порог отклонения убран из поиска (§ 5, § 6)

Спецификация предполагала жёсткое отклонение `max(300 км, 150 км, 15 % × длина)`
для следующего груза. При сверке с полным перебором этот порог отбрасывал
цепочки, которые были выгоднее найденного решения, — та же ошибка, за которую
критиковался старый сборщик, только с другим числом.

Принято: **отклонение не ограничивается, а оценивается деньгами внутри поиска**
(порожний подъезд входит в расчёт шага). Радиус `startRadiusKm` применяется
только к первому плечу от базы — там, где он и имеет смысл по постановке
(«радиус от начала маршрута»).

### 12.2. Сравнение вариантов идёт по остатку с обязательством вернуться (§ 4)

В `Economics` появилось поле `netCommittedRub`: для маршрута, который не
возвращается на базу, из него вычтена стоимость возврата. Ранжирование
использует именно его — иначе «уехать и не вернуться» всегда выигрывает ровно
на цену возврата. В карточке показываются оба числа: настоящий остаток рейса и
остаток с возвратом. Режимы «обязательно» и «предпочтительно» не выбирают
рекомендацией открытый рейс; он показывается отдельно как «цена возврата».

### 12.3. Параметры региона участка — строгие, а не «по месту старта» (§ 3.2)

Для участка, пересекающего границу регионов, берётся коэффициент дороги —
максимум, скорость — минимум. Побочный эффект: `d(a,b) = d(b,a)`, чего при
«регионе старта» не было (расстояние зависело от направления расчёта).
