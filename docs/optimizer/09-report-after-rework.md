# Отчёт: что сделано после предложения нового варианта планировщика

Коротко: планировщик не «подлатан», а построен заново — от архитектурного
разбора и математической спецификации до выкатки, с независимым эталоном
(перебором) на каждом шаге. Ниже — что именно появилось, что проверками было
найдено и исправлено, какие цифры это подтверждают и что осталось открытым.

Даты: работа шла 1–2 ноября 2026. Ветка `main`, состояние на момент отчёта —
коммит `27828b7` (код — `7542819`), прод — `https://loginex-ochre.vercel.app`,
деплой `dpl_9CS9DwY2uvgAnLRNxC8Ck6u3K49u` (READY).

## 1. Что было предложено и что из этого выполнено

| предложение | состояние |
|---|---|
| Девять независимых компонентов с контрактами и своими тестами | **сделано**: Order Filter, Compatibility, Distance, Route Builder, Time, Capacity, Return, Economics, Optimizer — отдельные модули, ни одной «огромной функции» |
| Две модели: А (последовательные) и Б (сборные), со сравнением между собой | **сделано**: обе строятся на одном пуле, сравниваются по деньгам, победитель объясняется словами |

| Три понятия расстояния + отдельные участки (база→погрузка, погрузка→выгрузка, выгрузка→следующая погрузка, выгрузка→база) | **сделано**: `distance.ts` с `measured/estimated`, источники `osrm / exchange / estimate`, сегменты считаются по отдельности и попадают в расшифровку |
| Временная модель: движение, погрузка, выгрузка, ожидание окна, обязательные остановки, отдых, простой; календарь ≠ время движения | **сделано**: `time.ts`, календарь проверяется независимым расчётом (200 задач, 0 расхождений) |
| Экономика: эффективность, отдельные статьи, без двойного учёта, неизвестное видно | **сделано**: `economics.ts`, статьи раздельно (топливо, водитель, износ, шины, платные, прочие, постоянные), `null` для неизвестного, а не ноль |
| Возврат домой внутри построения, три режима, сравнение вариантов возврата | **сделано**: `returnMode` обязательно / предпочтительно / не важно, возврат с грузом и порожний сравниваются деньгами |
| Несколько вариантов с полной расшифровкой и ранжированием по пяти критериям | **сделано**: 3 варианта на машину + `variantsTotal`, ранжирование прибыль / прибыль на км / минимум порожнего / минимум времени / обязательный возврат |
| Эталонные сценарии и независимый перебор как эталон качества | **сделано**: 10 обязательных сценариев (`03-scenarios.md`) + два независимых перебора (`tests/routing-fixtures.mjs`, `tests/consolidated-fixtures.mjs`), сверка на тысячах задач |
| Производительность: предфильтрация, кеш расстояний, лимит состояний, замеры | **сделано**: кеш матрицы расстояний, бюджет состояний, статистика (состояния / отсечения / расстояния / попадания в кеш) в аудите |
| Строгий порядок этапов 1→6 | **соблюдён**: `01-architecture-review` → `02-math-spec` → `03-scenarios` → ядро → `05-integration` → проверки |
| Мультиарендность и мультирегиональность | **сделано**: изоляция по `organizationId` проверяется отдельно, база от организации/машины, часовые пояса и местное время, 5 баз в аудите |

## 4. Проверки: три независимых уровня

Независимость важна: отчёт, где ядро сверяется само с собой, ничего не
доказывает. Поэтому эталон — отдельный перебор, написанный другой рукой и не
вызывающий ни поиск, ни материализацию ядра.

### 4.1 Аудит сценариев — `npm run routing:audit`

| проверка | результат |
|---|---|
| модель А против перебора | 120 задач, расхождений **0**, худшее 0 % |
| календарь против независимого расчёта | 60 задач, расхождений **0** |
| сборка: улучшила / ухудшила | 40 задач: улучшила 1, ухудшила 0, невалидных 0 |
| сборка против перебора | same-origin 30/30, corridor 30/30, scattered 30/30 (худшее 0,01 %) |
| нарочно собранные задачи | 3 из 3: +66 855 ₽, +5 313 ₽, +41 663 ₽ к последовательной схеме |
| разные базы и вес | **20 из 20** (Ярославль, Москва, Екатеринбург, Краснодар, Красноярск × 1,5 / 5 / 10 / 20 т), нарушений 0 |
| производительность | 8 заказов — 21 мс, 5 611 состояний; 120 заказов — 365 мс, 300 965 состояний |
| изоляция | чужие заказы не протекают (`foreignOrdersLeak: false`), смена базы меняет первое плечо |

### 4.2 Массовая проверка на боевой базе — `npm run routing:mass`

18 прогонов (2 организации × пул 20/60/120 × горизонт 24/72/168 ч), 36
маршрутов. Для каждого плана проверяются календарь, время, пробеги (сумма
участков = общий пробег, порожний ≤ общего), отсутствие повторов заказов,
режим возврата, изоляция по `organizationId`, детерминизм (повторный расчёт
даёт ту же подпись) и отсутствие убыточных рекомендаций.

Итог: **нарушений валидатора 0, замечаний 0**, самый долгий расчёт 2 349 мс,
весь прогон 36 с. «ИП Фролов» — 5 машин из 5 с маршрутом при пуле 60 и 120
(при пуле 20 — 2, это ограничение пула, а не дефект). «ИП солнышко» — плана
нет с честной причиной: не задан адрес базы.

## 5. Дефекты, найденные проверками (и почему это не мелочи)

Это главная часть работы: почти всё найденное не падало тестами, а тихо
портило ответ.

| # | что было не так | чем это грозило | как исправлено |
|---|---|---|---|
| 1 | «Лучшего ещё нет» в сборной модели считалось нулём | на пуле, где всё убыточно, поиск сборки убивался целиком: −70 733 ₽ вместо −13 043 ₽ | «пока ничего не найдено» = `null` / `−∞` |
| 2 | Недоминируемость сравнивала время и **километры** | километр с грузом дороже порожнего, водитель оплачивается сменами — «короче» ≠ «выгоднее»; терялись лучшие порядки на 5–6 грузах | узел поиска хранит деньги пробега (км-расходы + точное топливо по весу) и часы за рулём; сравнение по трём величинам |
| 3 | Нижняя граница остатка пути требовала заново посетить погрузку уже погруженного груза | граница завышалась, отсечение по деньгам выбрасывало лучшую сборку: набор `{c1,c3,c4}` не давал ни одного законченного маршрута | для оставшегося груза в дерево входит либо обе точки, либо только выгрузка |
| 4 | Выручка «за километр» считалась фиксированной в отсечении | на таких наборах «длиннее, но выгоднее» отрезалось как заведомо убыточное | отсечение по деньгам на `perKm`-наборах отключается |
| 5 | Отчёт проверки печатал «водитель 0 ₽» | читалось как «водитель бесплатный», хотя оплата сидела внутри ставки ₽/км | статья внутри ставки называется своим именем; платные дороги — отдельной строкой |
| 6 | Отказ объяснялся «не окупает пробег», когда настоящая причина — лимит 72 ч | логист искал не ту причину и менял не то | причина называется та, что сработала |
| 7 | 1 город из 678 без координат, часть адресов грязная | грузы молча выпадали из пула | 677/678, отброшенных по координатам — **0**, мусор в адресах чистится |
| 8 | Прогрев справочника принимал «0 городов» за сбой и глотал ошибку запроса | прогрев «проходил», ничего не прогрев | «0 городов» = «уже есть»; ошибка возвращается наверх |
| 9 | Эндпоинт отдавал все варианты: 143 КБ на 5 машин, до 1,8 МБ в худшем | экран тормозил, а «показали три» читалось как «нашли три» | три варианта + `variantsTotal`; разбор запроса вынесен в `api.ts`, 11 тестов контракта |
| 10 | Поиск пересчитывал состояния там, где хватало кеша | 120 заказов упирались в секунды | меньше аллокаций и состояний, качество не изменилось |

Сценарий-иллюстрация к п. 1–3: `scattered-148` до правок давал −70 733 ₽ против
эталонных −13 043 ₽; `scattered-31` — −30 569 ₽ против −29 964 ₽ и полностью
обрезанный набор; после правок оба совпадают с перебором до рубля.

## 6. Интеграция и выкатка

* Сервер считает всё на своей стороне (`app/api/logist/routing/plan`), клиент
  только показывает: правила оплаты, региональные параметры и настройки
  организаций остаются на сервере.
* В ответе на машину — 3 варианта; у каждого: последовательность остановок,
  карта, расстояния участков, общий и порожний пробег, календарная
  длительность, даты, выручка, расходы по статьям, результат, возврат домой,
  предупреждения, достоверность и объяснение рекомендации.
* Если план не строится — это `ok: false` с первой причиной словами и
  кнопками «откуда строить», а не пустой экран.
* Выкатка: `main` = `7542819` (+ документация `27828b7`), деплой
  `dpl_9CS9DwY2uvgAnLRNxC8Ck6u3K49u` — READY, эндпоинт отвечает (403 без
  сессии — то есть жив и закрыт).

## 7. Что осталось открытым (честно)

1. **Оптимум сборной цепочки доказан не всегда.** Перебор как эталон работает
   для наборов до трёх грузов; на 5–6 грузах план помечается `exact: false`, и
   это сказано в интерфейсе. Совпадение с перебором на 450 задачах — сильное
   свидетельство, но не доказательство: редкий случай может встретиться на
   другом пуле, и ловить его будет `routing:mass-quality`, а не отчёт.
2. **Свой OSRM не поднят в проде.** Клиент, проверка и `deploy/osrm/` (compose,
   карта, nginx с лимитами) готовы, но пока расстояния берутся из биржевой базы
   и оценки по прямой с коэффициентом региона. Достоверность в плане помечена:
   `measured` / `estimated`.
3. **Оплата водителя по правилам организации** (`perKm`, `perHour`, `mixed`)
   делает деньги зависимыми от распределения гружёного хода — там отсечение по
   деньгам отключено. Это медленнее, но не теряет оптимум.
4. **Вторая организация не даёт плана** — не задан адрес базы. Это данные, а не
   код: маршрут не от чего строить, и планировщик так и говорит.
