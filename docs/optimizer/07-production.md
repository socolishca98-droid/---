# Планировщик в бою: что выкачено и чем проверено

Дата: 2 ноября 2026. Коммиты `c02b341` (ядро и подключение), `2d1041e` (этот отчёт),
`953a098` (в ответе API — три варианта на машину). Прод —
`https://loginex-ochre.vercel.app`, деплой `dpl_6Qhu5CrzHLDKfFeqXwoFy5stad7W`.

## Что выкачено

Новое ядро маршрутизации (`lib/routing`, 15 модулей) влито в `main` и работает
на проде. Экран помощника (`/lm/routes/assistant`) больше не считает цепочку в
браузере: он спрашивает `POST /api/logist/routing/plan`, а браузерный сборщик
остался аварийным путём и честно пишет в причинах маршрута, что цепочка собрана
упрощённо.

Почему сервер, а не браузер: строгий перебор цепочек — это второй сборщик,
который неизбежно разойдётся с серверным. Два разных ответа на один вопрос хуже,
чем один медленный.


Все 5 планов прошли независимый валидатор ядра: вес и объём на каждом участке,
порядок погрузок/выгрузок, окна, возврат на базу.

**Что видно из этого прогона (и это записано, а не спрятано):**

1. **27 из 120 грузов отброшены из-за отсутствия координат** — в справочнике
   городов ATI у боевой базы не было колонок `lat`/`lon`. Миграция добавлена
   (см. ниже), данные заполняются по мере расчётов: геокодер пишет в `GeoCache`
   (сейчас 1523 адреса), и следующий расчёт берёт город уже оттуда.
2. **Одно плечо на машину** при 93 грузах в пуле — следствие не ядра, а данных:
   у большинства грузов одна и та же пара городов и ставка, а отбраковка по
   координатам срезает ровно те грузы, из которых складывается цепочка. По
   мере заполнения справочника цепочки удлиняются сами.
3. **«Оптимум доказан: нет»** у четырёх машин — честная пометка: перебор
   наборов был ограничен бюджетом состояний. Ядро не выдаёт эвристику за
   доказанный оптимум.

## Что изменено в боевой БД

Одна аддитивная миграция, без изменения данных:

```sql
alter table "AtiCity" add column if not exists lat double precision;
alter table "AtiCity" add column if not exists lon double precision;
```

Причина: схема проекта (`prisma/schema.prisma`) описывает у `AtiCity`
координаты, а в боевой базе колонок не было — сервис расчёта на каждом плане
получал ошибку запроса и молча уходил в геокодер. Сверка остальной схемы с
базой расхождений не нашла: 33 таблицы, все скалярные поля на месте.

## Как повторить проверку

```bash
npm ci
npm run test:build
node audit/routing-quality.mjs               # качество против перебора
node --test tests/routing-*.test.mjs         # 68 тестов ядра
npm run routing:check -- <organizationId>    # живой прогон по базе
```

Проверка на боевых данных (только чтение) описана в этом же файле шагами:
пул грузов, парк, координаты из `AtiCity`/`GeoCache`, затем `planFleet` и
`validatePlan` по каждой машине.
