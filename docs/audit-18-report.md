## C. Новые обнаруженные проблемы

### C1. Изоляция организаций — ДЫР НЕ НАЙДЕНО (CONFIRMED, положительный результат)
Живой эксперимент: две компании зарегистрированы через штатный API, в org B
созданы заказ, водитель, машина, рейс. Под админом org A выполнено 14 попыток
кросс-доступа (GET/PATCH/DELETE заказа, водителя, машины, рейса, документы,
расходы, карта, история) — **все заблокированы** (404/403/400). Утечек в
списках (заказы, водители, рейсы, машины, сотрудники, карта) нет. 9 публичных
маршрутов без сессии — 401/403. Итого **33/33 проверки пройдены**, тестовые
данные удалены (остатков 0).

**Вывод:** серверная изоляция (`scopedWhere` + `requireStaffOrganization`) работает
последовательно — это главный положительный результат этапа.

### C2. Бизнес-цикл — проходит целиком (CONFIRMED, положительный результат)
Регистрация → водитель/машина → заказ → согласование → рейс → старт → расход
(ремонт) → оплата → доставка (agreed→in_route→control→delivered) → завершение →
документы (ttn,waybill,contract) → экспорт отчёта → бухгалтерский экспорт:
**23/23 шага**. Ошибочные данные отклоняются корректно (вес −10 → 400, расход −500
→ 400, расход 999 999 999 → 400, несогласованный заказ в рейс → 409 с текстом).
Матрица переходов статусов (`lib/orders/stages.ts:197`) не даёт поставить
недопустимый статус. Транзакции на завершении рейса и удалении заказа — есть.

### C3. Новые проблемы (по приоритетам)

**P1 — блокирует безопасный пилот**

**P1-1. Жёсткое удаление заказа стирает деньги и историю переговоров** — CONFIRMED
- Файл: `app/api/orders/[id]/route.ts:505-507` (DELETE), схема
  `prisma/schema.prisma:358` (`OrderNegotiation.order onDelete: Cascade`).
- Сценарий: админ удаляет доставленный/оплаченный заказ → заказ, вся переписка
  (торг, ценовые предложения) удаляются физически; оплата (`isPaid`) исчезает из
  бухгалтерского экспорта.
- Факт: DELETE без проверки `status`/`isPaid`, каскад снимает переговоры.
- Ожидание: запрет удаления оплаченных/доставленных (или soft-delete +
  «корзина»), либо предупреждение с требованием причины.
- Доказательство: чтение кода + `grep onDelete` + эксперимент (заказ с
  `isPaid: true` удалён в изолированной орг, оплата пропала из экспорта).

**P1-2. Нет процедуры восстановления из бэкапа и нет расписания бэкапов** — CONFIRMED
- Файлы: `scripts/db-backup.mjs` (есть), `lib/backup/plan.mjs`, `vercel.json` (пусто).
- Сценарий: сбой прод-базы → бэкап есть только если кто-то запускал вручную;
  восстановление — ручные `sqlite3 .dump`/`psql` по подсказке в логе.
- Факт: бэкап запущен вручную и работает (2036 КБ), но **скрипта `db:restore`
  нет**, расписания нет, `sqlite3` CLI не установлен (копирование файлом при
  живой БД может быть несогласованным), подсказка восстановления для Postgres
  показывает файл `.db` — неверная инструкция.
- Ожидание: расписанная процедура восстановления + проверенный прогон restore на
  копии + расписание (cron) хотя бы ежедневного бэкапа.

**P1-3. Проблемы из отчёта №17, оставшиеся блокерами пилота** — CONFIRMED ранее
(подтверждены на этапе 2 чтением кода): нет кнопки документов в карточке рейса
(`app/lm/routes/[id]/page.tsx` — 0 упоминаний «документ»), нет кнопок экспорта в

## E. Непроверенные предположения (нужны окружение/доступ/решение владельца)

1. **Прод-переменные Vercel** (`SMTP_*`, `VAPID_*`, `CRON_SECRET`, `SENTRY_DSN`,
   `OWNER_EMAIL`, `NEXT_PUBLIC_CARTO_API_KEY`) — что реально задано, проверено
   только по прошлым записям; требуется доступ к дашборду или выгрузка имён
   переменных (не значений!).
2. **Состояние боевой PostgreSQL** — применены ли все миграции, совпадает ли
   схема; требуется доступ к БД только на чтение (`\d "Photo"` и т.п.).
3. **Восстановление из бэкапа на PostgreSQL** — требуется тестовая копия БД.
4. **Push-уведомления вживую** — нужен браузер с разрешением и подпиской.
5. **Нагрузка** — нужен стенд с реальными объёмами (заказы, фото, чат).
6. **Выбор почтового провайдера** для отправки документов (пользователь запретил
   платные сервисы без согласия) — решение владельца.
7. **Политика хранения/удаления данных** (soft-delete vs hard) — решение
   владельца; от неё зависит объём работ по P1-1.

## Честный итог: что закрыто, что нет, что нужно для пилота

мутирующих API (PATCH/POST/DELETE — только точечно).
