# Технический отчёт: переработка ETA и исполнения рейсов

Дата: 2026-10-15. Ветка: `feat/profile-edit`. Коммитов по задаче: 16 (с `50eb999` по `7c97006`), 53 файла, +11 637 строк.

Отчёт написан по факту проверок. Где пункт не доведён — сказано прямым текстом, без «почти готово».

## 1. Что было не так (три критические проблемы)

1. **Четыре независимые формулы ETA для одного рейса.** Кабинет водителя считал
   время своей формулой (`остаточное расстояние ÷ 60 км/ч × старые коэффициенты`),
   посегментный прогноз — своей, превью в заказах — своей, мобильный ETA — своей.
   Для одного рейса получались три разных времени прибытия.
2. **Рейс не имел единой модели исполнения.** Не было последовательности этапов
   (база → погрузка → плечо → выгрузка → возврат), поэтому погрузка и выгрузка
   учитывались с разной точностью в разных местах, а пересчёт после события мог
   посчитать одну и ту же операцию дважды.
3. **Перерывы не сдвигали часы рейса.** Модель знала про нормы отдыха, но не
   встраивала паузу в расписание: последующие плечи считались так, будто водитель
   ехал без остановки.

Плюс: PostgreSQL-миграция отсутствовала (блокер), на `/api/eta/*` не было
ограничения частоты при обращениях к внешним API, `next build` в песочнице
не запускается по памяти.

## 2. Что сделано

### 2.1. Единая модель рейса (`lib/eta/trip.ts`)

Рейс описывается **последовательностью этапов**, а не суммой независимых оценок.
Виды этапов: `driving`, `loading`, `unloading`, `documents`, `waiting`, `rest`,
`return_to_base`.

* `buildRouteStages(orders, { origin, returnToBase, actuals, stopDurations })` —
  строит шкалу. Сортировка по `routeSequence` (заказы без `sequence` — в конец),
  лишних плеч нулевой длины не создаёт, рейс, заканчивающийся на базе, не получает
  плечо возврата. Плечо до склада идёт **до** этапа погрузки (см. §9).
* `calculateTripEta(stages, options)` — прогноз по шкале. **Своей формулы ETA в
  модуле нет**: движение считает движок `forecastSegments`, операции передаются
  ему же как остановки. Плановые времена этапов берутся у движка
  (`arrivalAt`/`departureAt` его сегментов), поэтому шкала включает остановки и
  перерывы и не расходится с итогом.
* Завершённые этапы не пересчитываются как будущие (их длительность фактическая).
  Текущему этапу движку отдаётся **остаток** остановки — иначе проведённое на
  складе время посчиталось бы дважды.
* Плечо без расстояния оценивается haversine × 1.3 и явно помечается
  (`dataQuality.estimatedLegs` + предупреждение), а не выдаётся за маршрут.
* На выходе: следующая точка с адресом/операцией/расстоянием/ETA, оставшееся
  время по категориям, возврат на базу, три сценария, факторы, качество данных,
  источники, признак достоверности.

### 2.2. Временная шкала и обязательный отдых (`lib/eta/driver-rest.ts`, `lib/eta/forecast.ts`)

`createRestTracker(rules, priorDrivingMinutes)` — инкрементальный планировщик:
после каждого сегмента часы двигаются, и при необходимости в них **вставляется
пауза**, поэтому следующие плечи считаются на сдвинутый момент (час пик, сезон,
погода). Остановки не сбрасывают непрерывность. Приоритет: лимит смены 600 →
`daily_rest` 660, иначе 270 → `break` 45. Нормы берутся из `FleetSettings`
организации (`restDriveLimitMin`, `restMinBreakMin`).

Особый случай — пауза после последнего плеча: она вставляется **внутри** плеча
(сдвиг `departureAt`), иначе рейс из одного длинного плеча показывал прибытие без
обязательной паузы. Если время управления до выезда неизвестно — в прогноз
попадает `rest.warning`, а не молчаливое допущение.

### 2.3. Единый серверный расчёт (`lib/eta/trip-repository.ts`)

Загрузка данных из базы и приведение их к форме чистой математики. Источник
истины об исполнении — **существующая** модель `RouteStage` (раньше почти не
использовалась: писали только демо-сиды, читал один мобильный эндпоинт).
Параллельной сущности не заводилось.

* `ensureRouteStages` — идемпотентное создание недостающих этапов + сверка:
  этапы, которых больше нет в модели, удаляются **только если по ним нет
  фактических отметок**. История не удаляется.
* `listRouteStageIds` — индекс этапа рейса → строка `RouteStage`, чтобы команда
  водителя попала именно в показанный на экране этап.
* `getRouteTripEta` — прогноз по рейсу. Организация обязательна и стоит в каждом
  условии запроса.

### 2.5. Кабинет водителя (части 11–12 ТЗ)

* `lib/eta/trip-actions.ts` — машина состояний этапа: `availableTripActions`
  (что показать) и `checkTripCommand` (что разрешить). Один модуль на браузер и
  сервер, поэтому показанная кнопка не может быть отклонена — это проверяет
  отдельный тест.
* `POST /api/m/route/stage` — серверное применение команд. Сервер сам определяет
  текущий этап: «закрыть» точку, до которой водитель не доехал, нельзя; рейс не
  завершается с незакрытыми этапами. Отметки пишутся в `RouteStage` и дублируются
  в `RouteEvent` (`type=stage_command`) как неизменяемая история.
* Защита от повторной отправки на двух уровнях: `clientEventId` (повторный запрос
  отвечает «уже принята», ничего не меняя) и условие в `update` (отметка ставится
  только если её ещё нет).
* `components/driver-mobile/trip-stage-panel.tsx` — активный рейс, кнопки **только
  по текущему этапу**, прогноз, фактические отметки, «сообщить о проблеме».
  Кнопки и этапы приходят с сервера; своей формулы ETA в браузере нет.
* `recalcLiveEta` в мобильном API заменён единым механизмом (ключи ответа
  сохранены, чтобы не ломать интерфейс).

### 2.6. Помощник сборки (часть 13 ТЗ)

`lib/logist-mobile/assistant-eta.ts` + `POST /api/logist-mobile/assistant/compare`
+ экран сравнения. Пять показателей «до/после»: длина, время движения, операции,
перерывы, длительность; плюс возврат на базу и нарушения сроков заказов. У каждого
показателя — объяснение, почему он изменился. `delta` точно равен разнице
показываемых чисел.

Альтернатива **не создаёт записей в БД** — проверено вживую: количество рейсов до
и после сравнения не изменилось. Рейс создаётся отдельным запросом после
подтверждения логиста.

### 2.7. PostgreSQL-миграция (часть 16 ТЗ) — сделана ранее в этой задаче

## 4. Живой прогон полного цикла рейса (демо-данные, HTTP)

Рейс `demo-route-4`, драйвер `+79161234504`, база — Домодедово:

1. `GET /api/m/route` → кнопка «Начать рейс», прогноз: движение 27320 с, операции
   9000 с, перерыв 2700 с, всего 39020 с; 4 этапа; честные предупреждения
   («у 1 плеча расстояние оценено по прямой ×1.3», «погода не учтена»).
2. `start_trip` → этап 0 (погрузка на базе) → «Начать погрузку».
3. `start_operation` → «Погрузка завершена». Повторный вызов с тем же
   `clientEventId` → `{duplicate: true}`, ничего не изменено.
4. `finish_operation` → «Начать движение». `start_driving` → «Прибыл».
5. `arrive_point` → этап выгрузки → «Начать выгрузку» → «Выгрузка завершена».
6. `start_driving` (возврат на базу) → «Прибыл» → «Завершить рейс».
7. `finish_trip` → рейс завершён, оставшееся время 0.

Контрольные отказы (все с причиной дословно для водителя, HTTP 409):
* `start_driving` на этапе погрузки → «Сейчас не движение»;
* `arrive_point` без начатого движения → «Движение не начато: отмечать прибытие нечему»;
* команда на чужой этап → «Этап не является текущим. Действия выполняются по порядку»;
* `finish_trip` с незакрытыми этапами → «Остались незавершённые этапы (2). Их нельзя пропускать».

Итог в базе: 4 строки `RouteStage` с фактическими отметками, 12 записей `RouteEvent`,
статус рейса `completed`, `startedAt`/`completedAt` заполнены. Мусорные строки
этапов от прежней версии строителя удалены сверкой.

Сравнение «до/после» на живых заказах: длина 3373.4 → 3267.9 км (−105.5),
движение 4123 → 3868 мин (−255), операции 300 → 300 (без дублей), перерывы без

обнаружено и объяснено. Записей в БД не создано.

## 5. Что было найдено и исправлено по ходу (настоящие дефекты)

Живая проверка вскрыла три дефекта, которых не видели модульные тесты:

1. **Плечо до склада шло после этапа погрузки.** Водителю предлагалось грузить до
   приезда на склад. Исправлено, закрыто регрессионным тестом.
2. **Расстояние заказа проставлялось каждому плечу заказа.** `Order.distance` —
   это расстояние от погрузки до выгрузки, а плечу **до** склада оно тоже
   доставалось: длина рейса удваивалась. Плечам добавлен признак `leg`
   (`to_pickup`/`to_dropoff`), расстояние берётся только у `to_dropoff`.
3. **Отметки движения не возвращались в прогноз.** `RouteStage` писали `startedAt`
   для `driving`/`return_to_base`, но `buildRouteStages` не читал факт по ним:
   водитель отмечал «начал движение», а прогноз считал этап будущим. Ключ
   фактических отметок теперь включает номер этапа.

Плюс: `ensureRouteStages` строил этапы без базы и без возврата на базу, поэтому
этап «возвращение на базу» не имел строки `RouteStage` — команда на нём отвечала
«Этап рейса не найден». Строитель вынесен в одну функцию на все три потребителя.

Отдельно: защита от дубликатов не срабатывала — `RouteEvent.data` это строка JSON
со всей полезной нагрузкой, а сравнивалась она с голым `clientEventId`. Исправлено
на поиск вхождения.

## 6. Модель коэффициентов — без двойного учёта

Взёшенная сумма коэффициентов разбавляла факторы (вечерний пик ×1.8 превращался
в ×1.28). Заменена на **перемножение**. Факторы применяются один раз, в движке;
операции передаются ему как остановки и не участвуют в перемножении.

Действующие значения: нейтральный набор → 1.0; вечерний пик → ×1.8; ночь → ×0.85;
снег → ×1.35; городской участок <20 км → ×1.3; oversized → ×1.3; потолок ×2.5.
Городской час пик: 07–09 ×1.5, 16–19 ×1.55; пригород ×1.3/×1.4; загородная ×1.05.

Сезон учитывается через явную модель. **Погода выключена по умолчанию**
(`ETA_WEATHER != "on"`): Open-Meteo free tier — только некоммерческое
использование, коммерческие тарифы платные, и подключать их без согласия
пользователя нельзя. При отключённом источнике API честно возвращает
`weatherAvailable: false`, `sources.weather: "unavailable"` и предупреждение —
а не молчаливые нули.

**Актуальных пробок по России нет.** TomTom не покрывает РФ, у Яндекса и 2GIS
нет детальных пробок в маршрутизации. Поэтому используется различение:
исторический трафик (внутренние коэффициенты по часу и дню недели) ≠ типичная
загруженность ≠ текущие пробки (недоступны) ≠ подтверждённое ДТП (недоступно).
В отчёте и интерфейсе не заявляется ни одного из двух последних.

Ограничения маршрута влияют на **допустимость**, а не только на время: модель
`RouteRestriction` проверяет проезд (негабарит, высота, вес), и при нарушении
этап помечается, а не «медленнее едет».

## 7. Безопасность

* Организация берётся из проверенной сессии и стоит **в условии запроса**, не в
  фильтре интерфейса. Чужой id → 404, а не «нашлось и обновилось».
* Ранняя дыра в `/api/eta/forecast` (явные `origin`/`destination` + чужой
  `routeId` пропускали проверку принадлежности) исправлена: владелец ресурса
  проверяется всегда, когда id приходит в теле.
* Авторизация, CSRF и изоляция организаций не отключались. Поле `driverId` из
  тела запроса не принимается — автор события всегда из сессии.
* Ограничение частоты считает через существующий лимитер с распределённым
  бэкендом, а не через локальную память одного экземпляра.
* Ссылки из тела (`vehicleId`, `stageId`, `orderId`) проверяются на
  принадлежность организации до записи.
* Таймауты и кэш: погодный клиент — таймаут 9 с, кэш 10 мин, батч не более 6
  точек. Геокодирование — кэш `GeoCache` + паузы между запросами.

## 8. Миграции и откат

Миграции ETA идут **не** через `prisma/migrations/`, а по конвенции проекта:
`prisma/sql/<дата>-<имя>.sql` + `prisma db execute`. Отдельный
`.postgres.sql` для прода и `.sql` для разработки, выбор — по протоколу
`DATABASE_URL`. `prisma/schema.postgres.prisma` генерируется
`npm run schema:postgres` и в git не отслеживается.

Откат: миграция идемпотентна (`CREATE TABLE IF NOT EXISTS`), поэтому повторный
прогон безопасен. Откат — удаление таблицы `EtaForecast` и её индексов; удаление
рейса обнуляет `routeId` у прогнозов (SET NULL), удаление организации удаляет их
каскадом. Оба поведения проверены на реальном PostgreSQL.

Исправлено: `docs/eta-migration.md` утверждал, что удаление рейса удаляет
прогнозы (на самом деле SET NULL) и предписывал нерабочий путь для прода.

## 18. Оставшиеся старые механизмы ETA и почему

1. **`lib/eta/service.ts` — `calculateETA` («одно число на маршрут»).** Остаётся
   как общий хелпер, но больше не вызывается ни из оптимизатора, ни из API
   прогноза: все три сценария (водитель, логист, оптимизатор) считает
   `lib/eta/trip.ts`. Удалять не стал намеренно — в разделе 15 перечислены
   места, где он мог бы понадобиться, и требование промпта было «не удалять
   старую реализацию, пока не перенесены все её необходимые сценарии».
2. **`lib/eta/coefficients.ts` — `describeCoefficients`** больше не вызывается
   оптимизатором (объяснение коэффициентов теперь идёт из единого движка через
   `why`). Функция остаётся: она используется тестами и может понадобиться для
   разбора факторов.
3. **Оценка времени на карте логиста без рейса** (`estimateDurationMin` в
   `app/api/dashboard/routes/route.ts`). Для «solo»-групп (заказы без рейса)
   единый движок неприменим — некуда цеплять этапы. Панель об этом говорит
   прямым текстом, а не подставляет число как прогноз.
4. **`updateForecast` по-прежнему не вызывается.** Версии теперь делает
   `saveForecast` (каждый расчёт — новая строка), поэтому «обновление строки на
   месте» не нужно нигде. Функция оставлена как есть, без удаления.

## 21. PostgreSQL-миграция

Проверялась на **настоящем PostgreSQL в WebAssembly (PGlite)** — отдельная
чистая база, production не затрагивался. 15/15: состав колонок сверен с

применения, каскады при удалении.

Новая миграция `prisma/sql/2026-10-15-eta-forecast-stages.postgres.sql`
добавляет одну nullable-колонку `stagesJson` через `ADD COLUMN IF NOT EXISTS`,

песочнице (`prisma/verify.db`), колонка на месте.

Production-база не трогалась.

## 22. Production-сборка — НЕ ПРОВЕРЕНА

`npx next build` в песочнице падает: **код выхода 137 (OOM)**. В окружении
1.9 ГБ RAM / 2 CPU, из них доступно ~1.4 ГБ; сборка Next.js 16 + Turbopack
убивается ядром на этапе «Creating an optimized production build». Пробовал с
`--max-old-space-size=1400` и с остановленным dev-сервером — результат тот же.

Это **непроверенный пункт**, а не «сборка проходит». Перед слиянием в main
необходимо прогнать `next build` в окружении с достаточной памятью (Vercel
превью-деплой или машина от 4 ГБ).

## 23. Оставшиеся проблемы

1. **Production-сборка не проверена** (раздел 22) — блокер для слияния в main.
2. **Уверенность прогноза низкая по умолчанию** (0.11 на оптимизаторе):
   причина честная и системная — нет геометрии дорог по классу, погодного
   источника и истории операций. Платные API пробок и погоды по решению
   пользователя не подключаются, поэтому уверенность остаётся низкой, пока не
   накопится собственная история фактов.
3. **Нет GPS в реальном времени.** Панель карты говорит об этом прямым
   текстом и не подставляет вычисленную точку. Источника реальных координат в
   проекте нет — заявлять GPS-точность нельзя.
4. **Ветка не запушена** (нет `GH_PAT`). Пуш только через
   `scripts/push-branch.sh` и только по разрешению пользователя.
5. **Браузерная проверка вёрстки** новых блоков (перерывы, история прогноза)
   по HTTP и типам выполнена, но визуально в браузере не подтверждена.

## 28. Уверенность (`confidence = 0.11`) — что это такое

Код: `lib/eta/forecast.ts`, функция `assessConfidence` (строка ~515).
В оптимизаторе `riskScore = Math.round((1 - confidence.score) * 100)`,
поэтому `riskScore 89` ⇔ `confidence.score 0.11`.

**Формула — произведение множителей, а не вероятность:**

```
score = 1
сегментов 0                → 0
полное перекрытие          → 0.05
× средняя уверенность класса дороги   (0.2 … 0.9, lib/eta/road-class.ts)
× 0.8   если погоды нет   (или × 0.7, если прогноз дальше 5 суток)
× уверенность в ТС        (0.9 / 0.7 / 0.5 / 0.3 — по числу неизвестных полей)
× 0.9   если время операций взято из диапазонов по умолчанию
× 0.3   если маршрут имеет недопустимые ограничения
× 1.15  если использована история по сегментам (не выше 1)
итог зажимается в 0.05 … 1; уровень: ≥ 0.7 high, ≥ 0.45 medium, иначе low
```

На живом рейсе 0.11 — это «класс дороги не определён (шаги OSRM без номера
и узнаваемого названия) × нет погоды × неполные данные ТС × время операций
из диапазонов по умолчанию». Точный состав каждого прогноза хранится в
`confidenceReasonsJson`.

**Трактовка:** это **эвристика самодиагностики**, а не измеренная точность.
Множители подобраны вручную, калибровки по фактам не проводилось. Единственная
сейчас накопленная ground truth — `errorMinutes` из `recordActual`
(живой цикл дал −94 мин). До статистики по накопленным фактам утверждать
«точность 11 %» нельзя; правильно — «прогноз грубый, и движок сам об этом
говорит». Формулу не менял.

## 37. Дефекты, найденные при приёмке

**37.1. Nominatim не работал вовсе (исправлено).**
`lib/geo/geocode.ts` задавал `USER_AGENT = "Loginex-TMS/1.0
(маршрутизация заказов)"`. Кириллица в значении заголовка недопустима, и
`fetch` в Node бросает `TypeError: Cannot convert argument to a ByteString…`.
Ошибка перехватывалась, писалась в лог и превращалась в `null` — то есть
**ни один** адрес не геокодировался через Nominatim, при этом наружу это
выглядело как «координат нет».

Доказательство (отладочный маршрут на живом сервере, тот же URL):
`User-Agent` с кириллицей → TypeError; ASCII `User-Agent` → **HTTP 200**;
без заголовка → 403. Побочно: тесты эту поломку не видели, потому что
подменяют `fetch` заглушкой — реальная проверка заголовков не выполняется.

Исправлено на `USER_AGENT = "Loginex-TMS/1.0 (route planning)"` (ASCII,
осмысленное значение — политика Nominatim требует непустой User-Agent).
После правки, с очищенным кешем и **без** ключа Яндекса, Nominatim
загеокодировал все адреса, и ETA считается реальным OSRM (раздел 35).
Это правка дефекта, а не новая функция: восстанавливается задуманное
поведение «без ключа — бесплатный Nominatim».

**37.2. Частичный отказ геокодера молча выпадает (НЕ исправлено — нужно
решение).** Предупреждение «не определены координаты N заказ(а) из M»
срабатывает только когда не построилось **ни одного** плеча
(`lib/eta/trip.ts:742`, условие `legs.length === 0`). Если не геокодируется
один заказ из трёх, его этапы просто не строятся, а оставшиеся складываются
в более короткий и правдоподобный маршрут: в эксперименте плечо

## 41. Ложные координаты: что происходило

**Симптом.** На заведомо несуществующий адрес «Хреново-Никудаево,
несуществующая область, Нетакаяландия» Яндекс.Геокодер отвечает HTTP 200 и
одной точкой `61.698657, 99.505405` (Эвенкия). Формально это валидные
координаты: проверка диапазона (`isCoordinates`) их пропускает. В итоге рейс
«становился» 10 329 км с ETA на 11.6 суток, а `dataQuality` заявлял
`allLegsGeocoded: true` и `reliable: true`.

**Причина.** У ответа Яндекса на ложный адрес `kind: "country"` и
`Address.formatted: "Россия"` — провайдер не нашёл ничего и вернул центр
страны. У честного совпадения («Тула, Тульская область») `kind: "locality"`,
`Address.formatted: "Россия, Тула"`. Проверка `found !== "0"` не помогает:
Яндекс считает, что нашёл. Единственный надёжный признак — `kind`.

**Исправление.** `lib/geo/geocode.ts`: ответ Яндекса с `kind === "country"`
теперь считается отказом (как и `found === "0"`). Для Nominatim добавлен
аналогичный барьер: `class === "place" && type === "country"` — отказ.

## 42. Причина сбоя Nominatim

**Симптом.** С очищенным кешем и без ключа Яндекса не геокодировался **ни
один** адрес: `sources.routing` становился `"fallback"`, плеч было ноль.

**Причина.** В `lib/geo/geocode.ts` был задан
`USER_AGENT = "Loginex-TMS/1.0 (маршрутизация заказов)"`. Кириллица в
значении HTTP-заголовка недопустима, и `fetch` в Node бросает
`TypeError: Cannot convert argument to a ByteString because the character at
index 17 has a value of 1084 which is greater than 255`. Ошибка перехватывалась
в `geocodeNominatim`, писалась в лог и превращалась в `null` — то есть отказ
выглядел как «координат нет», а не «запрос не ушёл».

Доказано на живом сервере отладочным маршрутом (тот же URL, тот же адрес):

| вариант | результат |
|---|---|
| `User-Agent` с кириллицей (как в коде) | `TypeError: Cannot convert argument to a ByteString…` |
| ASCII `User-Agent: Loginex-TMS/1.0` | **HTTP 200** |
| без заголовка `User-Agent` | HTTP 403 (Nominatim блокирует undici по умолчанию) |

**Почему тесты это не видели:** они подменяют `fetch` заглушкой, поэтому
реальная проверка заголовков Node не выполняется. Платный ключ Яндекса
маскировал поломку: ответ Яндекса шёл другим путем без кириллицы в заголовках.

**Исправление.** `USER_AGENT = "Loginex-TMS/1.0 (route planning)"` — ASCII,
непустое значение (политика Nominatim требует осмысленный User-Agent).
После правки, с очищенным кешем и **без** ключа Яндекса, Nominatim
геокодирует все адреса, ETA считается реальным OSRM.

## 43. Прочие дефекты, исправленные по итогам приёмки

**43.1. Молчаливый пропуск негеокодированных заказов.**
Предупреждение «не определены координаты N заказ(а) из M» жило внутри
`if (legs.length === 0)`, то есть срабатывало только когда не построилось
**ни одного** плеча. При частичном отказе (один битый заказ из трёх) его этапы
просто не строились, оставшиеся точки складывались в более короткий и
правдоподобный маршрут, а `allLegsGeocoded` показывал `true`.

Исправлено в `lib/eta/trip.ts`: предупреждение выдаётся всегда, когда
`unlocatedOrders` не пуст, и **перечисляет адреса** (до пяти, остальное —
счётчиком), потому что логисту нужно знать, что исправлять.

**43.2. `allLegsGeocoded` отражал только построенные плечи.**
`legs` содержит лишь те плечи, которые удалось построить, поэтому флаг
означал «у всех построенных плеч есть расстояние», а не «весь рейс
геокодировался». Разделено на две независимые проверки:

- `legsHaveDistance` — у каждого построенного плеча есть расстояние;
- `allLegsGeocoded` — `legsHaveDistance` **плюс** ни один заказ не остался
  без координат.

Предупреждение «не у всех плеч есть расстояние» теперь завязано на
`legsHaveDistance`, иначе после исправления 43.1 оно срабатывало ложно на
маршрутах, где все построенные плеча имеют расстояние.

**43.3. Подпись плеча врала про место.** В `buildRouteStages` адрес курсора
обновлялся безусловно (`cursorAddress = order.routeTo`), даже когда
`order.to` не геокодировался. После заказа с неразрешимой выгрузкой подпись
плеча возврата на базу утверждала «Такогогороданет → база», а координаты
плеча оставались в предыдущем городе. Исправлено: курсор и его адрес двигаются
только когда точка действительно известна.
