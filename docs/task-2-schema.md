## 2. Как это устроено

### 2.1 Модель `Route`

```prisma
model Route {
  id            String    @id @default(cuid())
  name          String?                       // «Ярославль → Иваново → Санкт-Петербург»
  status        String    @default("planned") // planned | active | in_transit | completed | cancelled
  driverId      String?
  driver        Driver?   @relation(fields: [driverId], references: [id], onDelete: SetNull)
  vehicleId     String?
  vehicle       Vehicle?  @relation(fields: [vehicleId], references: [id], onDelete: SetNull)
  startedAt     DateTime?
  completedAt   DateTime?
  totalDistance Int?
  totalCost     Int?      // расходы рейса (задача 10: топливо по чекам)
  fuelExpense   Int?
  cargoWeight   Int?
  cargoVolume   Float?
  notes         String?
  orders        Order[]
  stages        RouteStage[]
  events        RouteEvent[]
}
```

Статус рейса **не вводится руками наугад** — он выводится из статусов заказов
(`deriveRouteStatus`) и проверяется на допустимость перехода (`canTransitionRoute`):

| Из | Можно в |
|---|---|
| `planned` | `active`, `in_transit`, `completed`, `cancelled` |
| `active` | `planned`, `in_transit`, `completed`, `cancelled` |
| `in_transit` | `active`, `completed`, `cancelled` |
| `completed` | — (терминальный) |
| `cancelled` | `planned` (вернуть в план) |

Недопустимый переход отдаёт `409` с человеческой причиной, а не молча ломает данные.
Каждый переход пишется событием `RouteEvent.type = "status"` в таймлайн рейса.

Отменённый статус пересчётом не «оживляется»: это решение диспетчера.

### 2.2 Связь «водитель ↔ машина» — одна запись

`lib/fleet/assignment.ts` — единственное место, где эта связь меняется:

- `linkDriverToVehicle(db, driverId, vehicleId | null)` — закрепить/снять;
  автоматически отвязывает предыдущего водителя этой машины и обновляет кэш;
- `unlinkVehicle(db, vehicleId)` — отвязать всех (перед удалением машины);
- `refreshVehicleCache(db, vehicleIds)` — обновить кэш после правки машины
  (сменили госномер или тип);
- `syncDriverVehicleCache(db, driverId)` — привести кэш к данным машины;
- `findVehicleOccupant(db, vehicleId, exceptDriverId?)` — кто сейчас на машине.

Функции принимают либо `prisma`, либо клиент транзакции — запись атомарна.

`Driver.vehicleType` и `Driver.vehiclePlate` остались как **кэш** (его читают
мобильное приложение водителя, карта и списки), но пишутся теперь только здесь.

### 2.3 Форма ответов API не сломана

Клиенты (страницы, диалоги, мобильное приложение) ждут прежние поля, поэтому:

- `GET /api/routes/[id]` по-прежнему отдаёт `route.{id, driver, vehicle, orders, stats, capacity}`,
  рядом появились `status`, `statusLabel`, `name`, `startedAt`, `completedAt`, `notes`;
- в `stats` сохранены старые имена (`totalWeight`, `totalPrice`, `completedOrders`)
  и добавлены новые (`cargoWeight`, `cargoVolume`, `revenue`, `activeOrders`, `cancelledOrders`);
- `POST /api/routes` по-прежнему возвращает `{ success, routeId, ordersCount }` + `route`;
- списки машин (`/api/fleet`, `/api/fleet/vehicles`) по-прежнему содержат `driverId` —
  теперь это **производное** поле из `Driver.vehicleId`, а не колонка таблицы.

## 3. Применение (по шагам)

```bash
# 0. резервная копия базы
cp prisma/dev.db ~/loginex-dev-backup-$(date +%F-%H%M).db

# 1. зависимости (обновлены next/react — см. раздел 6)
npm install

# 2. диагностика данных ДО изменения схемы
#    сохранит снимок Vehicle.driverId в prisma/.task2-vehicle-links.json
npm run db:migrate-task2 -- --check

# 3. применить схему (данные сохраняются; согласитесь на удаление Vehicle.driverId)
npm run db:push
npm run db:generate

# 4. перенос данных: создаст строки Route, выровняет связь и кэш
npm run db:migrate-task2

# 5. проверки
npm run verify:task2     # схема + код: 15 проверок, база не нужна
npm test                 # 57 тестов (24 из них — модель рейсов)
npm run typecheck        # типы
```

Если `db push` недоступен (нет сети для движков Prisma, например), схему можно
применить запасным SQL — он идемпотентен и проверен на копии вашей базы:

```bash
npm run db:sql:routes
npm run db:migrate-task2      # досчитает имена рейсов и кэш водителей
```

SQL создаёт таблицу `Route`, индексы, уникальный индекс `Driver.phone`,
переносит рейсы из `Order.routeId` (статус и итоги считаются по заказам)
и выравнивает кэш. Чего SQL **не** делает (в SQLite это пересоздание таблиц,
умеет только `db push`): добавление `FOREIGN KEY` к существующим таблицам и
физическое удаление колонки `Vehicle.driverId` — готовый блок пересоздания
есть в файле закомментированным (раздел 6).

### Порядок запуска важен

`--check` до `db push` — потому что колонка `Vehicle.driverId` исчезнет,
а скрипт умеет читать её заранее сохранённый снимок. Если сначала сделать
`db push`, данные не потеряются, но восстановить закрепление «со стороны машины»
можно будет только из снимка.

## 4. Чек-лист проверки руками

После `npm run dev`:

**Маршруты** (`/routes`)
- [ ] список открывается, рейсы берутся из таблицы `Route` (в сети один запрос
      `GET /api/routes?status=...` вместо трёх);
- [ ] у рейса видно имя («Ярославль → Иваново»), статус, число точек;
- [ ] «Завершить рейс» → статус `Завершён`, у водителя закрылась смена, машина свободна;
- [ ] «Отменить рейс» → статус `Отменён`, незакрытые точки отменены,
      **доставленные остались доставленными** (раньше отменялись все подряд);
- [ ] повторное завершение уже завершённого рейса → понятная ошибка, а не 500;
- [ ] «Добавить догруз» → пересчитались итоги и имя рейса.

**Сборка рейса** (`/orders` → песочница → «Оформить рейс»)
- [ ] рейс создался, в базе появилась строка `Route` (`npm run db:migrate-task2 -- --check`
      покажет `создано рейсов: 0`, то есть расхождений нет);
- [ ] машина с превышением грузоподъёмности не проходит (400 с цифрами);
- [ ] машина, уже закреплённая за другим водителем, не отдаётся (409 с именем водителя).

**Автопарк** (`/fleet`)
- [ ] у машины виден закреплённый водитель — тот же, что в карточке водителя;
- [ ] закрепить водителя за машиной → в карточке водителя сразу правильный госномер и тип;
- [ ] снять машину с водителя → госномер и тип **обнуляются** (раньше оставались «призрачные»);
- [ ] удалить машину → у водителя пропадает и номер, и тип.

**Водитель** (мобильный контур `/m`)
- [ ] выбор машины: чужая закреплённая машина не отдаётся (409);
- [ ] точка GPS, фото и SOS пишутся в таймлайн рейса (`RouteEvent`),
      в том числе для «старых» рейсов, созданных до миграции.

**Проверка curl** (нужен вход логиста — см. `docs/task-1-security.md`, раздел 4):

```bash
# список рейсов (без cookie ожидаем 401)
curl -sk https://localhost:3000/api/routes | head -c 300

# рейс целиком: статус, имя, заказы, итоги, utilisation
curl -sk https://localhost:3000/api/routes/<routeId> | python3 -m json.tool | head -40

# недопустимый переход статуса → 409 с причиной
curl -sk -X PATCH https://localhost:3000/api/routes/<routeId> \
  -H 'Content-Type: application/json' -d '{"status":"planned"}'
```

## 7. Осознанно отложено (не забыть)

- **`SosAlert.respondedBy` / `resolvedBy`** оставлены строками: это «кто отреагировал»,
  а не внешние ключи с каскадным удалением; переводить на `User` логичнее в задаче 8–9,
  когда появится экран разбора инцидентов.
- **`Route.totalCost` / `fuelExpense`** пока пустые: их заполнит задача 10
  (расходы рейса из распознанных чеков).
- **`RouteStage`** описан в схеме и связан с `Route`, но точки-этапы ещё не создаются
  кодом — это задача 6 (визуализация сегментов) и задача 10 (таймлайн рейса).
- **SQLite и внешние ключи**: `db push` включит FK-ограничения. Если база уже большая,
  проверьте после переноса, что не осталось заказов с `routeId` в никуда —
  `npm run db:migrate-task2 -- --check` это показывает (раздел 4).
- **Переход на Postgres** — задача 13 (обсуждаем отдельно).
- **`npm run typecheck`** сейчас даёт 72 ошибки вместо 91 до правок: все они
  предсуществующие (`noImplicitAny` на колбэках Prisma и 13 обращений к полям
  объектов без типа). Часть исчезнет сразу после `npm run db:generate` —
  сейчас в песочнице клиент Prisma не сгенерирован, поэтому типы запросов
  вырождаются в `any`. Новых ошибок задача 2 не добавила.
