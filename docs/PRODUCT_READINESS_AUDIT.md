# Аудит готовности продукта Loginex

**Дата:** 17 октября 2026
**Ветка:** `feat/profile-edit` (коммит аудита — отдельно, без push и без слияния в `main`)
**Окружение:** песочница, SQLite `prisma/verify.db`, production-сборка `next build && next start`, браузер Chromium headless
**Статус аудита:** read-only по продуктовому коду — доказательная картина. Далее выполнены точечные исправления подтверждённых дефектов (раздел 8).

## 4. Интерфейс в браузере (этап 4)

Проверка шла **в настоящем браузере** (Chromium headless, вход через форму, production-сборка), а не по коду. Страница считается сломанной, если показан Error Boundary «Что-то сломалось» — такого не видно по HTTP-коду.

**Итог: 65 страниц → 57 ✅ · 4 ⚠️ · 2 ❌**

### Сломанные страницы

| Страница | Что видит пользователь | Причина (доказана) |
|---|---|---|
| **`/drivers`** | Error Boundary «Что-то сломалось», данные не показаны | `app/drivers/page.tsx:538` рендерит `{driver.rating \|\| 5.0}`. `GET /api/drivers` возвращает `rating` **объектом** `{deliveredTotal, onTime, docs, score, grade}` (живой ответ подтверждён). React error #31 «Objects are not valid as a React child» с ровно этими ключами зафиксирован в консоли. Тот же объект в строке 273 ломает средний рейтинг (`sum + {…}` → NaN). Правильно обращается `components/fleet/driver-card.tsx` (`driver.rating.score`) — /fleet работает |
| **`/reset-password`** | Error Boundary | Клиентская страница тянет `MIN_PASSWORD_LENGTH` из `@/lib/auth/password`, а тот импортирует `promisify` из `node:util`. В браузере: `TypeError: The "original" argument must be of type Function at e.promisify` на этапе оценки модуля. SSR-HTML при этом чистый — падает только клиент |

### Частично

`/routes/[id]`, `/clients/[id]`, `/drivers/[id]` → **404, таких страниц не существует** (есть только API и `lm/*` версии). `/m` отдаёт мало текка — экран строится на данных рейса, при пустом рейсе почти пуст.

### Что работает

Все 7 публичных страниц, 19 кабинетных desktop-экранов, `/owner`, `/owner/journal`, `/print/route/[routeId]`, `/orders/[id]`, все 20 страниц мобильного логиста `lm/*`, все 9 страниц водителя `m/*`. Вход через форму на desktop и на мобильном — ✅.

## 7. Итоговая сводка

### По статусам модулей

| Статус | Страницы (браузер) | Сценарии A–O | Роли |
|---|---|---|---|
| ✅ VERIFIED | 57 | 9 | 4 |
| ⚠️ PARTIAL | 4 | 3 | 0 |
| ❌ BROKEN | 2 | 2 | 0 |
| ➖ MISSING | 0 | 1 | 0 |
| ❓ NOT TESTED | 0 | 0 | 0 |

Тесты: **965 зелёных (588 + 377) и 1 красный (node --test)**. Сборка: EXIT=0.

### Пять главных блокеров

1. **P0 — `/drivers` не открывается.** Error Boundary из-за рейтинга-объекта, отрисованного как число. Основной экран работы с водителями недоступен. Правка точечная: `app/drivers/page.tsx` строки 273 и 538 + локальный тип `rating` привести к контракту `/api/drivers` (`{score, grade, …} | null`), как уже сделано в `components/fleet/driver-card.tsx`.

2. **P0/P1 — восстановление пароля сломано.** `/reset-password` падает на импорте `node:util` в клиентский бандл. Правка точечная: вынести `MIN_PASSWORD_LENGTH` в модуль без node-импортов (рядом с `lib/auth/constants.ts`).

3. **P1 — прогресс рейса не виден диспетчеру.** `start_trip` пишет `Route.status = "in_progress"` — значения нет в словаре `ROUTE_STATUSES`. Диспетчерский API нормализует его в `planned`, подпись показывает сырое `in_progress`. Правка точечная: писать `in_transit`.

4. **P1 — прогноз завышает доверие.** `reliable: true` при `allLegsGeocoded: false` и `confidence 0.09`. Поле `reliable` не смотрит на качество данных.

5. **P0 (коммерческий) — нет тарифов и оплаты.** Нечем брать плату за продукт. Это не дефект кода, а отсутствующая функция; без неё «работать и платить» невозможно.

Дополнительно, но быстро: `CRON_SECRET` не задан (сканирование ATI выключено), `SENTRY_*` не заданы (ошибки продакшена невидимы), `/api/health` не проверяет базу, манифест API-документации устарел на 24 эндпоинта и краснит `npm test`, нет desktop-страниц рейса, клиента и водителя.

### Разделение по требованиям аудита

**Подтверждённые проблемы** (дефект воспроизведён и причина найдена в коде): Б-1 `/drivers`, Б-2 `/reset-password`, Б-3 словарь статуса рейса, Б-4 `reliable` при неполных данных, Б-5 `/api/health` без базы, Б-6 Sentry выключен, Б-7 cron выключен, Б-8 нет страниц `[id]`, Б-10 манифест API, Б-11 маржа 100 % без предупреждения.

**Риски** (не дефект сейчас, но станет проблемой): миграции вручную вместо `prisma migrate`; 0 пользователей с ролью `logist` (роль не проверена в бою); пустые ключи ATI / 2GIS / Яндекс-маршрутизации; расходы не ведутся, поэтому отчёт о марже нерепрезентативен; уверенность ЕТА — эвристика, не откалибрована по `errorMinutes`.

**Непроверенные предположения** (в аудите не установлены): поведение под реальной нагрузкой многих организаций (в песочнице 1.9 ГБ ОЗУ, dev-сервер падал по памяти — это ограничение стенда, не продукта); работа на PostgreSQL в продакшене (схема `schema.postgres.prisma` есть, но боевой прогон в этом аудите не выполнялся); сценарий J не доведён до конца (12 шагов водителя — предел цикла, `finish_trip` защищён и требует завершения всех этапов); миграция существующих данных на новый словарь статусов заказов.

### Реалистичный следующий шаг

**Один приёмный прогон интерфейса и два точечных исправления, затем коммерческий блокер.**

Конкретно:
1. Починить `/drivers` и `/reset-password` — обе правки локальные, затрагивают 2 файла, и обе возвращают к рабочему состоянию уже имеющиеся экраны (не новую функцию).
2. Прогнать `scripts/audit/ui-errorboundary.cjs` повторно и требовать 0 сломанных страниц — это дешёвая автоматическая приёмка интерфейса, её сейчас нет в CI.
3. Починить словарь статуса рейса (`in_progress` → `in_transit`) и согласовать `reliable` с `allLegsGeocoded` — оба правки в одном месте, оба убирают ложные сигналы диспетчеру.
4. Задать `CRON_SECRET`, `SENTRY_DSN`, `NEXT_PUBLIC_SENTRY_DSN` в окружении Vercel (значения присылает пользователь) и добавить проверку базы в `/api/health`.
5. Обновить манифест `npm run docs:api`, чтобы `npm test` был зелёным.
6. **И только после этого** — тарифы и оплата: без них продукт не может «работать и платить», и это единственный блокер, который нельзя закрыть правкой существующего кода.

Ветка не пушилась, в `main` не вливалось, production-база и production-деплой не трогались.

### 8.3 Какие сценарии пройдены

Сквозной цикл на изолированных тестовых данных, с проверкой факта в базе после каждого шага, а не только HTTP-кода ответа:

1. **Заказ** — три заказа созданы (Москва → Зеленоград → Тверь → Ржев), обязательные поля заполнены.
2. **Согласование** — все три переведены в `agreed`; несогласованный заказ в рейс не попадает (409 с объяснением).
3. **Рейс** — создан с назначенным водителем и машиной; `driverId`/`vehicleId` сверены с базой; заказы получили `in_route`; шкала этапов материализована в `RouteStage` (11 этапов, все 3 заказа); этап возврата на базу присутствует.
4. **Назначение** — рейс в `planned`, водитель и машина привязаны.
5. **Все этапы** — 12 команд водителя ровно по тем кнопкам, которые отдаёт сервер (`trip.actions`), с проверкой отметок `startedAt`/`endedAt` в базе после каждой. Повторное «начать рейс» не создаёт вторую отметку.
6. **Расход и пробег** — расход рейса записан диспетчером; показание одометра с чека водителя сохранено как фактический пробег (`endOdometer`).
7. **Завершение** — рейс с незакрытыми этапами не завершается (409); после закрытия всех этапов `finish_trip` даёт `completed` + `completedAt`.
8. **Сохранение факта** — заказы стали `delivered`; прогноз сохранён; факт прибытия записан в прогноз (`actualArrivalAt`, `errorMinutes`), исходный прогноз не перезаписан.
9. **Отображение диспетчеру** — история рейса отдаёт `completed`; рейтинг водителя показывает `{"deliveredTotal":3,"onTime":1,"docs":0,"score":60,"grade":"удовлетворительно"}`.
10. **Повторные команды** — после завершения рейс не оживает; повторный `finish_trip` идемпотентен (`completedAt` не меняется).

### 8.4 Какие дефекты остались и что требует следующего этапа

**Не исправлялось сознательно (вне этапа 1):**

- **Тарифы и оплата отсутствуют** — единственный блокер, который нельзя закрыть правкой существующего кода. Без него продукт не может «работать и платить».
- `CRON_SECRET` не задан — сканирование ATI выключено (fail closed by design).
- `SENTRY_*` не заданы — ошибки продакшена невидимы.
- `/api/health` не обращается к базе.
- Нет desktop-страниц рейса, клиента и водителя (`[id]`).
- Расходы не ведутся systematically — отчёт о марже нерепрезентативен (100 % маржи при нуле расходов).
- Миграции применяются вручную (`prisma/sql/*.sql`) вместо `prisma migrate`.
- Роль `logist` не проверена в бою: в песочнице 0 таких пользователей.
- Ключи ATI / 2GIS / Яндекс-маршрутизации пусты.
- Уверенность ЕТА — эвристика; калибровка по накопленным `errorMinutes` не выполнялась.

**Осталось незаверённым в этом этапе:** миграция уже сохранённых записей `Route.status = "in_progress"` в базе. Совместимость обеспечивает `normalizeRouteStatus` (такие рейсы читаются и показываются как «В пути»), поэтому данные не потеряны и интерфейс корректен; но в самой базе старое написание остаётся до отдельной команды переноса. В текущей песочнице таких записей 0.

**Рекомендуемый следующий шаг:** коммерческий блокер (тарифы и оплата), затем `CRON_SECRET`/`SENTRY_DSN` в окружении и проверка базы в `/api/health`. Остальное — по мере появления реальных данных.
