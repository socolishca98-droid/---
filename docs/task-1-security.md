## 1. Что было и что стало

| Было | Стало |
| --- | --- |
| «Вход» логиста: клиент сам клал объект пользователя в `localStorage`. Пароль не проверялся нигде | Вход проверяется на сервере: `POST /api/auth/login` сверяет пароль с хэшем в БД |
| «Вход» водителя: телефон + название организации, `driverId` писался в `localStorage` и присылался в каждом запросе | Телефон + **пароль** (scrypt-хэш в БД). Сервер выдаёт подписанный токен, `driverId` клиент больше не передаёт |
| Три разных «сессии» в браузере: `driver_session`, `driverSession`, `driver_id`+`driver_name` | Одна серверная сессия в httpOnly-cookie + строка `Session` в БД. `localStorage` для авторизации не используется вообще |
| `middleware.ts` отсутствовал: любой `/api/*` открывал данные без проверки | `middleware.ts` закрывает все `/api/*` и все страницы, решение — по роли |
| Одна учётная запись «для всех», ролей нет | Таблица `User`: `admin`, `logist`, `driver`; статусы `pending` / `active` / `suspended` |
| Сотрудника нельзя было ни добавить, ни уволить | Регистрация → «ожидает одобрения» → логист одобряет на `/users`; увольнение = «закрыть доступ» (обратимо, сессии отзываются сразу) |
| Водитель мог прочитать чужой заказ/чат/SOS, подставив чужой `driverId` в query или тело | Каждый обработчик берёт `driverId` **только** из проверенной сессии и проверяет принадлежность записи |

## 2. Как это устроено (коротко)

**Пароли** — `lib/auth/password.ts`: scrypt (N=16384, r=8, p=1, 64 байта), соль 16 байт на
пользователя, сравнение в постоянном времени. Минимальная сложность: 8+ символов, буквы и цифры.

**Сессии** — `lib/auth/token.ts`, `lib/auth/session.ts`:
- токен формата JWT (HS256, Web Crypto) в httpOnly-cookie: `loginex_staff_session` (сотрудник)
  и `loginex_driver_session` (водитель);
- `httpOnly` + `SameSite=Lax` всегда; флаг `Secure` ставится в production-сборке
  (в dev — нет, чтобы вход работал и по https из `npm run dev`, и по http из `dev:webpack`);
- каждая сессия — строка в таблице `Session` (`jti`), поэтому её можно отозвать немедленно:
  выход, смена пароля, закрытие доступа, сброс пароля;
- срок жизни — `AUTH_SESSION_TTL_HOURS` (по умолчанию 12 ч);
- 5 неудачных попыток входа → блокировка на 15 минут (`MAX_FAILED_LOGINS`).

**Middleware** — `middleware.ts` + `lib/auth/access.ts` (чистая функция `classifyRoute`,
покрыта тестами):
- публичные: `/`, `/login`, `/register`, `/m/login`, `/api/auth/{login,logout,register,session}`, `/api/health`;
- `/api/ati/cron` — по `CRON_SECRET` (fail-closed: без секрета 503);
- `/m/*` и `/api/m/*` — водитель;
- общий доступ (роль + принадлежность записи проверяет обработчик): `/api/chat`, `/api/orders`,
  `/api/orders/:id`, `/api/drivers/:id`, `/api/drivers/:id/active-order`,
  `/api/routes/:id/complete`, `/api/routes/:id/events`, `/api/m/maintenance`,
  `/api/auth/change-password`;
- всё остальное — сотрудник. Неизвестный путь закрывается по умолчанию.
- API получает 401/403 JSON, страница — редирект на свой логин с `?next=`.
- Если `AUTH_SECRET` не задан или короче 32 символов, **сервер не стартует**:
  `instrumentation.ts` → `register()` вызывает `collectStartupIssues()` (`lib/auth/startup.ts`)
  и делает `process.exit(1)` с понятным текстом и командой генерации секрета.
  На фазе сборки (`next build`, `NEXT_PHASE=phase-production-build`) проверка пропускается —
  образ в Docker/CI собирается без `.env`, секрет задаётся в рантайме.
  Второй слой (если процесс всё же поднят, например контейнер без instrumentation):
  middleware отвечает 503 «Сервер не настроен» — «забыли настроить» не превращается в «открыли данные».

**Права на запись** — в обработчиках: `requireStaff`, `requireDriver`, `requireAnySession`,
плюс `isSelfOrStaff`, `canDriverAccessOrder`, `canDriverAccessRoute`. Пример:

```ts
export async function GET(request: NextRequest) {
  const auth = await requireDriver(request)
  if (!auth.ok) return auth.response
  const driverId = auth.value.driver.id   // из сессии, а не из query
  ...
}
```

## 3. Первый запуск

```bash
# 1. Зависимости (добавился server-only)
npm install

# 2. Конфигурация
cp .env.example .env        # если .env уже есть — просто добавьте в него новые ключи
```

Откройте `.env` и заполните **обязательные** поля:

| Переменная | Зачем | Как получить |
| --- | --- | --- |
| `AUTH_SECRET` | подпись сессионных токенов | `node -e "console.log(require('node:crypto').randomBytes(48).toString('hex'))"` |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | первый администратор | придумайте сами |
| `DRIVER_DEFAULT_PASSWORD` | стартовый пароль учёткам водителей из сида | придумайте сами, водители сменят при входе |
| `CRON_SECRET` | вызов `/api/ati/cron` планировщиком | `node -e "console.log(require('node:crypto').randomBytes(24).toString('hex'))"` |

```bash
# 3. Схема БД (данные сохраняются; migrate dev НЕ запускать — см. примечание в SQL-файле)
npm run db:push
npm run db:generate

# 4. Первый администратор + учётки для существующих водителей
npm run seed:auth

# 5. Запуск
npm run dev          # https://localhost:3000
```

Если `db push` недоступен — то же самое делает идемпотентный SQL: `npm run db:sql:auth`.

**Что делает `npm run seed:auth`:**
- создаёт администратора из `ADMIN_EMAIL` / `ADMIN_PASSWORD` (повторный запуск не дублирует);
- для каждой записи `Driver` создаёт `User` с ролью `driver`, логином = телефон, статус `active`;
- если `DRIVER_DEFAULT_PASSWORD` задан — он становится общим стартовым паролем водителей;
- если `DRIVER_DEFAULT_PASSWORD` пустой — каждому водителю генерируется **свой** временный
  пароль, список печатается в консоли, и учётка помечается `mustChangePassword`
  (при первом входе водитель попадёт на смену пароля);
- у водителей без распознаваемого телефона учётка не создаётся — скрипт печатает
  предупреждение, таких заводят вручную: `/users` → «Сбросить пароль».

**Аварийный вход.** Если в базе нет ни одной учётной записи, первая же регистрация на
`/register` становится администратором (иначе одобрять её некому). Сервер пишет об этом
предупреждение в лог, а экран регистрации показывает плашку. Как только пользователи
появились, эта ветка больше не срабатывает.

**Сессия живёт долго (проверка «внезапного разлогина»)**
0.4. Войти диспетчером (`/login`) и водителем (`/m/login`) в двух вкладках, оставить на

0.5. Если разлогин всё же случился — открыть DevTools → Network и посмотреть ответ

0.8. В каждой — нет белой страницы, нет ошибки в консоли браузера, списки и карта рисуются.

**Вход сотрудника**
1. `/` → редирект на `/login` (вы не вошли).
2. `/login`, неверный пароль → ошибка «Неверный email или пароль», вход не выполнен.
3. 5 неверных паролей подряд → «Слишком много попыток…», даже с верным паролем вход

4. Верный пароль (администратор из сида) → `/dashboard`, в шапке — ваше имя и роль.

**Регистрация и одобрение**
7. `/register` → новая заявка → сообщение «Заявка отправлена…». Войти с ней нельзя:
   «Учётная запись ещё не одобрена».
8. `/users` → вкладка «Ожидают» → «Одобрить» → пользователь может войти.
   Работает **и под логистом**, и под администратором. «Отклонить» у заявки — это `reject`:
   диалог подтверждения, заявка удаляется, использование инвайт-кода возвращается

   и кнопка «Перейти к заявкам».
9. `/users` → «Закрыть доступ» → причина → пользователь мгновенно вылетает из системы
   (его открытая вкладка получает 401 при следующем запросе), войти снова нельзя:
   «Доступ закрыт…».
10. «Восстановить» → вход снова работает.
11. «Сбросить пароль» → временный пароль показан один раз → вход с ним требует сменить
    пароль → после смены вход обычный.
12. Роль (`admin` / `logist`) меняется только у администратора и только у действующего
    сотрудника: у заявки роль показана текстом с пометкой «из кода» (она задана
    администратором при создании кода). Себя закрыть нельзя. Логисту недоступны
    «Закрыть доступ», «Восстановить», «Сбросить пароль» и «Снять блокировку»
    (сервер отвечает 403) — из управления сотрудниками ему доступны только заявки:
    одобрить и отклонить.

**Вход водителя**
13. `/m/login` → телефон + пароль из сида → `/m`, в шапке имя водителя.
14. С паролем `DRIVER_DEFAULT_PASSWORD` система просит сменить пароль

15. `/m/profile` → «Сменить пароль» → после смены старым паролем войти нельзя.
16. Выйти из `/m` → `/m/login`.

**Новый водитель**
17. «Автопарк» → «Добавить водителя» → имя + телефон → после сохранения появляется диалог
    «Доступ для водителя» с телефоном и временным паролем (кнопка «Копировать»).
18. Выйти из штаба, войти в `/m/login` под этим телефоном и паролем → система требует

19. Удалить карточку водителя в «Автопарке» → его открытая вкладка `/m` получает 401 при
    следующем запросе, войти снова нельзя («Доступ закрыт»).

**Изоляция данных (главная проверка задачи)**
20. Водитель А заходит в `/m/orders` → видит только свои заказы.
21. В той же вкладке водитель А открывает URL чужого заказа

23. Диспетчер в `/api/sos` видит список SOS с пагинацией, может «взять в работу» /
    «закрыть» — водитель получает уведомление.
24. Чат: логист и водитель видят только свою переписку; сообщение, отправленное водителем,

**Учётка водителя создаётся вместе с карточкой.** «Автопарк» → «Добавить водителя» →
сервер создаёт `Driver` и связанного `User` (роль `driver`, логин = телефон, статус `active`,
`mustChangePassword`) и возвращает временный пароль — он показывается в диалоге один раз,
есть кнопка «Копировать». Если телефон не распознан или уже занят, карточка всё равно
создаётся, а в интерфейсе появляется предупреждение, что доступ надо доделать вручную.
Удаление карточки водителя закрывает доступ его учётке и отзывает все её сессии.

**Удалено**
```

```

Из шапки убраны **неработающие** поиск и колокольчик с hardcoded-уведомлениями: они
вернутся настоящими в задаче 4 (поиск по заказам/водителям, уведомления из БД).
Боковые бейджи «6» и «1» в меню пока тоже захардкожены — их задача 4 заменит на данные из БД.

## 7. Осознанно отложено (не забыть)

- **Postgres вместо SQLite** — обсуждаем в задаче 13 (несколько водителей пишут GPS и фото
  параллельно; SQLite в этом месте упирается в блокировку записи).
- **Модель `Route`** — сейчас `routeId` это строка, а не связь. Задача 2.
- **Единый компонент оболочки страниц** — сейчас часть страниц собирает `Sidebar + Header`
  вручную, часть использует `PageLayout`. Задача 4.
- **Уведомления водителя** (`hooks/use-driver-notifications.ts`) хранятся в `localStorage`
  — это не авторизация, а кэш, но в задаче 4 они переедут в БД (модель Notification уже есть).
- **`confirm()` в `/m/profile`** при выходе — в задаче 3 все `confirm()/alert()` заменяются
  общим стилизованным диалогом.
- **`/api/m/vehicle` GET** отдаёт водителю весь автопарк — в задаче 7 ограничим своей машиной
  и свободными.
- Клиентские вызовы в `app/m/page.tsx` всё ещё добавляют `driverId` в query/тело — сервер
  эти значения **игнорирует** и берёт свои из сессии. Косметику уберу в задаче 3 вместе
  с остальными заглушками.
