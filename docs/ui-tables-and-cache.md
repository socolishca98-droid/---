# Интерфейс: единые таблицы и клиентский кеш справочников

Две вещи, которые чаще всего портили ощущение от работы в интерфейсе: каждая
страница рисовала список по-своему, а при каждом заходе заново ждала
справочники. Здесь описано, как это устроено теперь — чтобы новые страницы
делались сразу правильно.

## 1. Таблицы: один компонент на все списки

`components/ui/data-table.tsx` — единственное место, где описан вид таблицы:
рамка, шапка, отступы, появление строк, загрузка, пустое состояние.

```tsx
const columns: DataTableColumn<Client>[] = [
  { key: "name", label: "Клиент", cell: (row) => row.name },
  { key: "debt", label: "Долг", align: "right", cell: (row) => money(row.debt) },
]

<DataTable
  columns={columns}
  rows={clients}
  rowKey={(row) => row.id}
  isLoading={isLoading}          // покажет скелетон нужной ширины
  skeletonRows={7}
  empty={<Card>…пустое состояние…</Card>}
  onRowClick={(row) => openCard(row.id)}
/>
```

Что даёт:

- одинаковые шапка, отступы и появление строк (`stagger-in`) на всех страницах;
- скелетон строится по числу колонок — ничего не «прыгает» после загрузки;
- пустое состояние задаётся один раз на страницу, а не разметкой вручную;
- правый столбец описывается как `align: "right"`, а не классами в каждой ячейке;
- `frame={false}` — когда таблица уже лежит внутри своей карточки (отчёты);
- `density="compact"` — плотные таблицы отчётов (отступы `p-2` вместо `p-3`).

Переведены: клиенты, должники (оплаты), отчёты (клиенты, водители, машины),
сотрудники, коды приглашений в организации. Печатный бланк ТТН
(`app/print/route/[routeId]/page.tsx`) и предпросмотр импорта базы
(`components/clients/client-import-dialog.tsx`) остались со своей разметкой:
там важен не список, а точная печатная форма и липкие заголовки в диалоге.

Заготовки скелетонов — `components/ui/skeletons.tsx`:
`TableSkeleton`, `CardsSkeleton`, `KpiSkeleton`, `PhotoGridSkeleton`,
`FeedSkeleton`, `LinesSkeleton`, `Shimmer`. Анимация — класс
`.skeleton-shimmer` в `app/globals.css`; при `prefers-reduced-motion` она
отключается вместе с `stagger-in`.

## 2. Клиентский кеш справочников

`lib/client-cache.ts` (React-часть) и `lib/client-cache-core.ts` (ядро без
React — его же гоняют unit-тесты).

```ts
const data = await fetchJsonCached<{ clients: Client[] }>("/api/clients?limit=500")
```

Правила, которые важно помнить:

| Ситуация | Поведение |
| --- | --- |
| Данные моложе `ttlMs` (по умолчанию 60 с) | ответ из памяти, в сеть не идём |
| Несколько компонентов просят одно и то же | запрос один, остальные ждут его |
| Запрос упал | ошибка **не** кешируется, отдаётся последнее известное значение |
| Есть `peekCache(url)` | мгновенное чтение без обещаний — для первого рендера |
| `fetchJsonCached(url, { force: true })` | кнопка «Обновить» идёт мимо кеша |
| `invalidateCache(prefix)` | сброс после изменения данных (после сборки рейса, создания кода) |

Как это выглядит в компоненте: сначала `peekCache` — если данные уже
приходили, страница рисует их сразу, без экрана загрузки; затем тихо
перезапрашивается свежее.

Где применено: маршруты, фото, чат, сотрудники, организация, платежи,
клиенты, автопарк, водители, справочники в песочнице заказов и в
диалоге загрузки фото. После изменения данных страница сама вызывает
`invalidateCache(...)`, чтобы следующий заход получил свежее.

Проверки: `tests/client-cache.test.mjs` (ядро кеша),
`__tests__/ui/data-table.test.tsx` (таблицы), плюс общий прогон
`npm run test:unit`, `npx vitest run`, `npx vitest run --config vitest.isolation.config.ts`.
