## 1. Задача A — редактирование имени пользователя

### 1.1 Что уже было в системе

Редактирование отображаемого имени **было реализовано полностью** — дублировать страницы,
поля и API не потребовалось:

| Слой | Где | Что делает |
|---|---|---|
| API | `app/api/auth/profile/route.ts` | `GET` — свои данные; `PATCH` — имя и телефон. `userId` берётся **только из проверенной сессии**, параметра с чужим id в роуте нет |
| Валидация | `lib/profile.ts` | `normalizeProfileName`, `PROFILE_NAME_MIN = 2`, `PROFILE_NAME_MAX = 80`; пробелы схлопываются, имя из одних пробелов отклоняется |
| Шапка | `components/header.tsx` | диалог «Мой профиль» → `handleSaveProfile` → `PATCH` → `await refresh()` |
| Водитель | `app/m/profile/page.tsx` | `saveData` → `PATCH` → `updateDriver` + `refresh` |
| Логист | `app/lm/more/page.tsx` | `saveProfile` → `PATCH` → `refresh` |
| Запись в БД | `PATCH` | водитель меняет `User.name` и `Driver.name` **одной транзакцией**; `P2002` → понятная ошибка |
| Журнал | `lib/audit.ts` | каждое изменение пишется как `profile_update` |

Отдельного второго поля для той же информации в моделях нет: используется существующее
`User.name` (и `Driver.name` для карточки водителя).

### 1.2 Что проверено

**HTTP — `scripts/audit/verify-profile-name.cjs` → 17/17 VERIFIED, 0 BROKEN**
(`scripts/audit/report-profile-name.json`):

- профиль читается; имя меняется; новое имя лежит в БД; повторное чтение отдаёт его;
- отклоняются: пустое имя, имя из одних пробелов, длиннее 80, короче 2 символов;
- невалидные имена не изменяют запись;
- роль, tenant, статус доступа и email **не меняются**, даже если пришли в теле;
- чужая запись не изменяется подменой `id`/`userId` в теле;
- без сессии — 401;
- водитель: имя в учётке и в карточке меняется вместе;
- исходные имена возвращены;
- изменение попало в журнал.

**Браузер — `scripts/audit/verify-profile-ui.cjs` → VERIFIED**
(администратор, «Мой профиль» из меню пользователя в шапке):
новое имя появляется в шапке, меню и приветствии **без перезагрузки**, сохраняется после
перезагрузки, в форме профиля показывает новое значение.

**Браузер — `scripts/audit/verify-profile-ui-driver.cjs` → VERIFIED**
(водитель, `/m/profile`): новое имя появляется на странице профиля и на главной `/m`

## 3. Задача C — план развития пульта владельца

Оценка по девяти разделам. «Есть» = работает и проверено в этом аудите. «Сломано» = было
найдено и исправлено. «Нет» = отсутствует, реализовывать на этом этапе не требуется.

### 3.1 Обзор платформы — **P1 (почти готов)**

- **Есть:** всего компаний, сотрудников, водителей, машин, рейсов и заказов в работе,
  доставлено, клиентов; «Сейчас в программе» (живые сессии за 15 минут); «Входов сегодня»;
  заявки на доступ; закрытые доступы; последние 30 действий по всем компаниям.
  Цифры сверены с БД по двум организациям.
- **Сломано было:** ошибка загрузки выглядела как прочерки (исправлено).
- **Нет:** периода («за 7/30 дней»), трендов и сравнения «было/стало», выручки и маржи,
  разбивки по тарифам, карты с активными рейсами, алертов («компания молчит 3 дня»).
- **Что можно использовать:** `/api/admin/overview` уже считает всёNeed; модели
  `Route`, `Order`, `Session`, `AuditLog`, `Organization`.
- **Что нужно:** группировка по датам в `overview` (сейчас только `dayStart` и 15-минутное
  окно), отдельный `/api/admin/overview/trends`.
- **Приоритет: P1** — полезно, но не блокирует.

### 3.2 Компании — **P1**

- **Есть:** список всех компаний с цифрами, карточка компании (сотрудники, водители,
  журнал компании), поиск человека по всем компаниям, пустые состояния, 404 на
  несуществующую компанию.
- **Сломано было:** ложное «Сотрудников пока нет» при ошибке API (исправлено).
- **Нет:** создания компании из пульта, изменения названия/реквизитов, архивации,
  привязки владельца к компании, массовых операций, сортировки и фильтров списка
  (только поиск по человеку).
- **Модели:** `Organization`, `User`, `Driver`, `Vehicle`, `Route`, `Order`, `Client`.
- **Нужно:** `/api/admin/organizations` (POST/PATCH) с проверкой прав и журналом;
  фильтры по активности и дате создания.
- **Приоритет: P1** (создание и правка компании) / **P2** (архив, массовые операции).

### 3.3 Пользователи — **P1**

- **Есть:** все сотрудники и водители всех компаний с ролями, статусами, причиной
  блокировки, последним входом; закрытие/открытие доступа; «Завершить сессии»; запрет
  самоотзыва и действий над другим владельцем; запрет входа в закрытую учётную запись.
- **Сломано было:** входы и возвраты не журналировались, исполнитель в журнале был
  неопознан (исправлено).
- **Нет:** смены роли и перевода между компаниями из пульта, сброса пароля от имени
  владельца, принудительной смены пароля при следующем входе, просмотра полного профиля
  (документы, медсправка), поиска по компании + роли + статусу одновременно.
- **Модели:** `User`, `Driver`, `Session`, `AuditLog`.
- **Нужно:** `/api/admin/users/[id]/reset-password` (с генерацией и одноразовым показом),
  `/api/admin/users/[id]/role`.
- **Приоритет: P1** (сброс пароля и смена роли) / **P2** (остальное).

### 3.4 Подключение к компании — **P0 (почти готов)**

## 5. Задача E — три жалобы водителя (11-й промпт, скриншот с прода)

Жалобы пришли из приложения водителя на проде (`loginex-ochre.vercel.app`). Все три
причины — в том, что на проде лежит `main`, а нужные механизмы есть только в ветке.

### 5.1 «Не нашёл, где сменить имя»

- **В `main`** — 0 совпадений по смене имени во всех контурах: `app/m/profile/page.tsx`
  не отправляет `PATCH`, кнопки «Изменить» нет. Подтверждено сравнением с `main`.
- **В ветке** — `/m/profile` → «Изменить» → поле `#m-profile-name` → «Сохранить».
  Поле только для чтения до клика «Изменить», имя меняется и в `User`, и в `Driver`
  одной транзакцией (`PATCH /api/auth/profile`), иначе учётная запись и карточка
  водителя разъехались бы.
- **Проверка:** матрица ролей `verify-name-all-roles.cjs` (5/5) + шаг
  «водителю доступна смена имени» в `verify-driver-actions.cjs` (8/8).

### 5.2 «Не меняется статус, когда нажимаю погрузку; нужен таймер простоя»

- **Причина в `main`:** `POST /api/m/shift` умеет только «начать смену». Нажатие
  «Погрузка» приходит как `{action:"status", status:"loading"}`, обработчик этого не
  знает и отвечает `alreadyActive: true` — кнопка подсвечивается, время не пишется,
  `ShiftEvent` не создаётся. В `main` нет и каталога `lib/shift/` — журнала смены,
  итогов по группам и живого таймера там не существует.
- **В ветке:** каждое нажатие пишет событие в журнал смены, пересчитывает итоги
  («В пути / Погрузка / Выгрузка / Ожидание / Отдых / Заправка»), статус заказа
  переводится в «контроль», отдых дополнительно пишется в рейс (по нему считаются
  нормы). Таймер тикает локально от `statusSeconds` из ответа сервера.
- **Проверка (живой прогон, `verify-driver-actions.cjs` 8/8):** вход водителя →
  «Погрузка» → статус в API `loading`, на экране «Погрузка», таймер `00:02 → 00:04`,
  последнее событие журнала `status to=loading`, заказ `demo-order-3` → `control`,
  итоги смены учитывают погрузку. Скриншот `docs/audit-screens/taskE-driver-loading-timer.png`.

### 5.3 «Не отправилось фото»

- **Ветка работает:** выбор файла на `/m/photo` → `POST /api/photos/upload`
  (multipart) → файл в хранилище, запись `Photo`, чек и накладная распознаются OCR,
  при отсутствии сети фото встаёт в очередь и уходит само. Проверено живым прогоном:
  запись `Photo` создана, файл лежит на диске, тип `cargo_before`.
- **Но на проде этот же путь упадёт по другой причине — архитектурной.** В `main`
  файл пишется прямо в `public/uploads/...`, а на Vercel файловая система
  серверных функций **только для чтения** (кроме `/tmp`, который не переживает
  вызов). `writeFile` в `public/uploads` на Vercel всегда завершается ошибкой →
  500 → водитель видит «Не удалось загрузить фото». **Исправлено в ветке:**
  драйвер хранилища `db` (`STORAGE_DRIVER=db`) кладёт байты в запись `Photo`
  (см. раздел 6): проверено живым прогоном в обоих режимах, фото открывается
  через `/api/photos/file`. Для прода остаётся применить миграцию и включить
  переменную — по команде владельца.

## 6. Открытый вопрос: где прод должен хранить фото

**Решено владельцем продукта: байты фото в PostgreSQL** (выбор сделан в чате).
Ниже — что это значит и что уже сделано.

### 6.1 Почему так

На Vercel файловая система серверных функций **только для чтения**, поэтому
прежний путь «файл в `public/uploads`» там не работал: фото груза и чеков просто
не сохранялись (это и была жалоба «не отправилось фото»). Хранить байты в базе —
единственный вариант без внешних сервисов и без доплат: инфраструктура уже есть,
миграция аддитивная, откат — одной переменной окружения.

### 6.2 Что сделано

| Что | Где |
|---|---|
| Драйвер `db` в хранилище | `lib/storage.ts`: `storageKind()` понимает `STORAGE_DRIVER=db`; `readPhoto`/`photoExists`/`removePhoto` читают и чистят `Photo.bytes` по `storageKey` |
| Колонки под байты | `Photo.storageKey`, `Photo.bytes`, `Photo.mime` в `prisma/schema.prisma` (SQLite) и сгенерированной `prisma/schema.postgres.prisma` |
| Запись байтов | `app/api/photos/upload/route.ts`: при драйвере `db` запись и байты создаются одним обращением — отказ на середине невозможен |
| Ссылка и доступ не меняются | `Photo.url` прежний (`/uploads/…`), отдаёт `/api/photos/file` после проверки организации; прямой публичный доступ не включался и не включается |
| Миграции | `prisma/sql/2026-10-18-photo-storage.postgres.sql` (прод) и `prisma/sql/2026-10-18-photo-storage.sql` (разработка) |
| OCR | `lib/ocr/service.ts` читает файл через `readPhotoByUrl` — для db-драйвера байты берутся из той же записи |
| Тесты | `__tests__/isolation/photo-storage-db.test.ts` — 7 проверок: отдача из базы, content-type, отказ чужой организации и без сессии, отсутствие файла на диске, чтение старых дисковых фото |
| Живой прогон | `scripts/audit/verify-driver-actions.cjs` в обоих режимах: `local` — файл на диске, `db` — байты в базе; в обоих фото открывается (`HTTP 200`, `image/jpeg`) |

### 6.3 Что нужно сделать на проде (по команде владельца)

1. Применить миграцию: `node scripts/db-sql.mjs 2026-10-18-photo-storage`
   (PostgreSQL). Без неё колонок `bytes`/`mime`/`storageKey` нет, и драйвер `db`
   работать не будет.
2. Прописать в переменных окружения Vercel: `STORAGE_DRIVER=db`.
3. Пересобрать и выкатить ветку.

До этого на проде остаётся риск: фото, снятые водителем, не сохраняются.
Откат: убрать `STORAGE_DRIVER` (или вернуть `local`) — запись снова пойдёт на
диск; колонки можно оставить пустыми, на расчёты они не влияют.

## 8. Остаточные риски

1. **Запись журнала на каждый вход** добавляет запись в `AuditLog` при каждом успешном
   входе сотрудника и водителя. При активной эксплуатации это десятки тысяч записей в
   месяц — нужна политика хранения (см. 3.5, P2). Сама запись не блокирует вход.
2. **Владелец без организации** (`organizationId = null`) получает 403 на все org-API.
   Это правильно с точки зрения изоляции, но означает, что владелец не может завести
   себе рабочую компанию из интерфейса — только через сиды или миграцию.
3. **«Сейчас в программе» и «Входов сегодня»** считают строки `Session`, а не людей:
   несколько сессий одного человека дают завышение. Для оценки масштаба платформы это

4. **Журнал бесконечный** — роста таблицы нет предела, индексов под фильтры по дате нет.
5. **Полоса поддержки** рискуется компонентом `AccountSwitchBanner`, который подключён в

6. **Массовый список компаний** в интерфейсе пульта: в песочнице 2 организации, поэтому
   пагинация и поиск по десяткам компаний в интерфейсе не проверялись (в API лимит 500).
7. **Естественное истечение сессии владельца по времени** (`OWNER_SESSION_TTL_MINUTES = 30`)
   по-прежнему не наблюдалось: прогоны короче. Проверено только поведение с недействительным

## 10. Карта и сборка рейса (13-й промпт)

### 10.1 Что сказал владелец

После починки входа: «Заработало. Но посмотри, как это неопрятно выглядит» — про карту логиста
(сравнение с Яндекс Картами). И главное: «Я не понимаю, как собрать сложный маршрут с возвратом.
Чтобы он был выгоден компании. Чтобы мне только кнопку нажать, позвонить и согласовать с
организациями, что именно мы повезём».

### 10.2 Что было не так (по коду, не по догадкам)

Карта:

1. **Подложка без подписей.** Своего ключа CARTO в проде нет, поэтому карта рисовалась
   подложкой Esri Dark Gray **Base** — серые пятна без названий городов, улиц и дорог.
   Отсюда и «неопрятно»: глазу не за что зацепиться.
2. **Цветные нити без подкладки** сливались с дорогами и застройкой.
3. **Цвет нити брался по номеру в списке** — при обновлении карты у одного рейса цвет менялся.
4. **Нить начиналась и заканчивалась ничем** — непонятно, где погрузка, а где выгрузка.
5. **Все нити одной толщины.** Их много — получается каша.

Сборка рейса:

6. **Помощник считал только выручку.** Топливо, себестоимость и прибыль не считались вовсе —
   вопрос «рейс выгоден компании?» программой не решался.
7. **Обратной загрузки не было.** Машина ехала обратно пустой — самый дорогой вид простоя,
   и помощник об этом молчал.
8. **Согласование — в другом экране.** Из предложения рейса нельзя было позвонить клиенту:
   кнопки «Позвонить» не было, нужно было уходить в карточку заказа.
9. **Не было сказано, в каком порядке работать.** Владелец буквально «тыкал и не понимал» —
   на экране не было шагов.

### 10.3 Что сделано

Карта (`components/logist-mobile/drivers-map.tsx`):

- Слой **подписей** Esri Dark Gray Reference поверх подложки (бесплатный, без ключа). Когда
  появляется свой ключ CARTO — подложка `dark_all` и так содержит подписи, и слой не нужен.
- Нить рисуется **двумя линиями**: тёмная широкая подкладка под цветной узкой.
- **Скруглённые концы и стыки** (`lineCap`/`lineJoin: round`) + `smoothFactor` — уходит
  «рваная лесенка» из прямых отрезков.
- **Точки «Погрузка» и «Выгрузка»** на концах нити: кольцо в цвете рейса с белой обводкой
  и подписью при наведении.
- **Цвет привязан к идентификатору рейса** — больше не «прыгает» между обновлениями.
- **Адаптивная толщина и выделение**: при большом числе рейсов линии тоньше; выбранный рейс
  толще и ярче, остальные приглушаются.
- Линии переведены в **SVG** (`preferCanvas: false`) — на плотном экране резче.
- **Честная плашка про пробки**: «Пробки в расчёте времени не учитываются — время считаем
  по километрам и опыту прошлых рейсов». Закрывается крестиком. Молчать нельзя: логист
  принимает решения по этим цифрам.
- Исправлен невалидный класс `shadow-sm/95` → `shadow-xl`.

Сборка рейса (`lib/logist-mobile/route-assistant.ts`, `app/lm/routes/assistant/page.tsx`):

- **Прибыль рейса**: выручка − топливо. Топливо считается по паспортному расходу машины
  с коэффициентом загрузки (`lib/fleet/fuel.ts`). Показываются литры, рубли и ₽/км.
- **Убыточный рейс** помечен красным и объясняется первым пунктом.
- **Честный отказ**: если у машины не заполнен расход топлива — прибыль не выдумывается,
  а показывается подсказка «Заполнить расход» со ссылкой в автопарк (флаг `needsFuelSetup`).
- **Обратная загрузка** (`findBackload`): помощник ищет среди согласованных заказов те,
  которые забирают там, куда рейс приезжает выгружаться. Сначала — груз в город отправления
  (машина возвращается домой загруженной), потом — любой груз из города выгрузки.
  Учитывается вместимость; если вместе с основным грузом не влезает — груз всё равно
  показывается с честной пометкой «нужна вторая машина», потому что логист может отправить
  часть заказов другим рейсом.
- **Кнопка «Позвонить»** у каждого заказа предложения и у каждого заказа обратной загрузки:
  согласование одним нажатием, без ухода в другой экран.
- **Порядок работы тремя шагами** в шапке: проверить состав и прибыль → позвонить клиентам
  и согласовать → нажать «Предложить рейс».
- Телефон клиента отдаётся в `GET /api/orders` (поле `clientPhone`, один join с `Client`).
