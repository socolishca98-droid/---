## 2. Порядок применения

### Шаг 1. Сгенерировать схему для PostgreSQL

```bash
npm run schema:postgres
```

Скрипт делает копию `prisma/schema.prisma` с datasource на `postgresql`
(`prisma/schema.postgres.prisma`). Файл в `.gitignore` — генерируется локально,
руками не правится.

### Шаг 2. Применить SQL к боевой базе

```bash
# DATABASE_URL боевой базы в окружении
npm run db:sql:eta
```

Скрипт делает `prisma db execute --file prisma/sql/2026-10-14-eta-forecast.sql`.
SQL идемпотентный: `CREATE TABLE IF NOT EXISTS` + `CREATE INDEX IF NOT EXISTS`,
повторный запуск безопасен. Foreign keys идут с `ON DELETE CASCADE`
(удаление рейса или организации удаляет прогнозы — прогноз без рейса бессмысленен).

**Важно:** в боевом контуре миграции этого проекта идут через `prisma/sql/`,
а не через `prisma/migrations/`. Это существующая конвенция (`db:sql:auth`,
`db:sql:routes`, `db:sql:push`); новой не заводил.

### Шаг 3. Сгенерировать клиент Prisma

```bash
npx prisma generate
```

После шага `prisma.etaForecast` доступен и в приложении, и в тестах.

### Шаг 4. Проверить, что таблица на месте

```sql
SELECT COUNT(*) FROM "EtaForecast";
-- 0 строк — нормально для свежей таблицы
```

### Шаг 5. Выкат

Прод-ветка `main`, слияние = выкат. Обязательно прогнать `next build`
до слияния (в песочнице разработки сборка падает по нехватке памяти —
это ограничение окружения, не регрессия кода; проверять на машине с
достатком RAM или в CI Vercel).

## 3. Переменные окружения

| Переменная | Обязательна | Значение по умолчанию | Зачем |
|---|---|---|---|
| `ETA_WEATHER` | нет | выключено | `on` — включать погодную модель Open-Meteo |
| `OPEN_METEO_API_KEY` | нет | — | ключ платного тарифа (домен `customer-api.open-meteo.com`) |
| `OPEN_METEO_BASE_URL` | нет | `https://api.open-meteo.com/v1/forecast` | свой базовый URL, если провайдер меняется |
| `TRAFFIC_PROVIDER` | нет | `historical` | источник пробочных данных; `historical` = только внутренняя история |

**Почему `ETA_WEATHER` по умолчанию выключен:** бесплатный тариф Open-Meteo
разрешён только для некоммерческого использования. Loginex — коммерческий
продукт, поэтому по умолчанию погода не запрашивается вовсе, а в интерфейсе
написано «погода выключена» с причиной. Включать только с платной подпиской.

**Если источник данных меняется** (другой погодный провайдер или платный
пробочный API) — правится только `lib/eta/weather/client.ts` и/или
`lib/traffic/service.ts`. Логика расчёта (`orchestrator.ts`, `segments.ts`,
`forecast.ts`) не меняется: она работает с готовыми числами, а не с форматом
конкретного провайдера.

## 4. Что происходит с данными

При каждом расчёсе через `POST /api/eta/forecast` сохраняется прогноз:
исходный расчёт, поправки, сегменты, версия коэффициентов, источники.
Через `POST /api/eta/forecast/[id]/actual` — фактическое прибытие и фактическое
время движения. По накопленным парам «прогноз/факт» считается точность
(`GET /api/eta/metrics`: MAE, медиана, доля в пределах 15 и 30 минут,
систематическое опережение/опоздание, разбивка по классам дорог, сезонам и погоде).

**Коэффициенты не меняются автоматически.** Нужна отложенная выборка и ручное
решение — на нескольких рейсах подгонка даёт переобучение.

## 5. Откат

1. Откат кода: `git revert` коммитов ETA (или переключение `main` на прошлый коммит).
   Обратная связь `Route.etaForecasts` исчезает вместе с моделью.
2. Таблицу можно не удалять: она ни на что не влияет, пока код её не читает.
   Если удалять — `DROP TABLE "EtaForecast";` (в PostgreSQL каскадом уйдут индексы;
   колонок в `Route`/`Organization` не добавлялось, так что чистить нечего).
3. Переменные окружения чистить не нужно: без `ETA_WEATHER=on` погода не включается.

## 6. Что НЕ менялось

- Существующий `calculateETA` (`lib/eta/service.ts`) и его кэш работают как раньше.
- `app/api/routes/calculate-eta/route.ts` и `app/api/routes/optimizer/route.ts` не тронуты.
- Бизнес-логика заказов, рейсов, экономики — без изменений.
