## 1. Что изменилось одной строкой

Раньше заказ рождался **в момент оформления рейса**, а до рейса груз жил строкой
общей таблицы `AtiCache` — без статуса, без заметок и без истории торгов. То есть
этапов «Поиск» и «Согласование» физически не существовало, а «статусы заказа»
жили в четырёх местах и не совпадали между собой.

Теперь:

- груз **берут в работу** из накопленной базы → создаётся `Order` своей
  организации на этапе «Поиск»;
- у заказа есть **лента согласования** (заметки, звонки, письма, документы, торг
  по цене) и автоматическая история смены цены/статуса;
- на **холст песочницы** попадают только согласованные заказы;
- **оформление рейса привязывает существующие заказы** (`orderIds`), а не создаёт
  их заново; машина и водитель на этом шаге **не обязательны**;
- все статусы заказа сведены в **один канон** — `lib/orders/stages.ts`.

Общая база ATI (`AtiCache`) больше **не помечается** при взятии груза: иначе груз
исчезал бы у других организаций. Принадлежность заказа строке базы хранится в
`Order.atiCacheId`.

## 2. Канон жизненного цикла заказа

Источник правды: `lib/orders/stages.ts` (чистый модуль, без Prisma и Next.js —
его можно импортировать и в клиентские компоненты, и в middleware).

| Этап | Статус | Подпись | Куда можно перейти |
|---|---|---|---|
| Поиск | `search` | В поиске | negotiation, agreed, rejected, expired, cancelled |
| Согласование | `negotiation` | Согласование | search, agreed, rejected, expired, cancelled |
| Согласование | `agreed` | Согласован | negotiation, in_route, documents, assigned, rejected, cancelled, expired |
| Маршрут | `in_route` | В рейсе | agreed, documents, assigned, control, cancelled |
| Документы | `documents` | Документы | agreed, in_route, assigned, control, cancelled |
| Назначение | `assigned` | Назначен | in_route, documents, control, agreed, cancelled |
| Контроль | `control` | На контроле | assigned, delivered, cancelled |
| Контроль | `delivered` | Доставлен | — (конечный) |
| Закрыт | `cancelled` / `rejected` / `expired` | Отменён / Отклонён / Неактуален | — (конечные) |

Правила переходов:

- заказ идёт **вперёд по процессу** и может быть **возвращён на шаг назад**
  (пересогласование, сняли с рейса, отменили назначение);
- **закрыть** можно с любого открытого статуса;
- из закрытых статусов не выходим: возврат в работу — отдельное осознанное
  действие, а не смена статуса;
- повторная установка того же статуса — не ошибка (no-op).

Детализация исполнения (погрузка / в пути / выгрузка / отдых) в статусе заказа
больше не живёт — она в `RouteStage` и `RouteEvent`.

### Прежние значения (легас)

Старые статусы принимаются и приводятся к канону функцией
`normalizeOrderStatus()`:

| Было | Стало |
|---|---|
| `new` | `search` |
| `processing`, `needs_clarification`, `proposed` | `negotiation` |
| `confirmed` | `agreed` |
| `loading`, `unloading`, `in_transit` | `control` |
| `completed` | `delivered` |

Поэтому **код работает и до переноса данных** — но перенос сделать нужно
(раздел 6).

## 3. Модель данных

`prisma/schema.prisma`:

**Order — новые поля**

| Поле | Зачем |
|---|---|
| `atiCacheId` | связь со строкой накопленной базы ATI; `@@unique([organizationId, atiCacheId])` — один груз берётся организацией один раз |
| `takenAt`, `takenById` | когда и кем груз взят в работу |
| `agreedPrice` | цена, о которой договорились (итог торга) |
| `negotiationStatus` | `new` / `in_progress` / `agreed` / `lost` (по умолчанию `new`) |
| `nextFollowUpAt` | когда вернуться к клиенту |
| `negotiations` | связь с лентой согласования |

Дефолт `Order.status` изменён `"new"` → `"search"`; все места создания заказа
теперь задают статус явно:

- `POST /api/orders/from-cache` → `search` (взяли из базы);
- `POST /api/orders` (вручную) → `negotiation`, а если сразу указаны рейс или
  водитель — `in_route` / `assigned`;
- `POST /api/routes` и `add-load` → `in_route`.

**OrderNegotiation — новая таблица** (лента согласования)

`id, organizationId, orderId, kind, text, priceOffer, authorId, authorName,
createdAt` + индексы `[orderId]`, `[organizationId]`, `[orderId, createdAt]`.

`kind`: `note`, `price_offer`, `call`, `email`, `document` — добавляет человек;
`price_change`, `status_change` — пишет **только сервер** (при смене цены или
статуса заказа), поэтому история торга не зависит от добросовестности логиста.

Новые индексы `Order`: `[status, organizationId]`, `[negotiationStatus]`,
`[nextFollowUpAt]`.

## 4. API

| Метод и путь | Что делает |
|---|---|
| `POST /api/orders/from-cache` | **Взять в работу**: `{ cacheId, fetchContacts? }` → заказ организации со статусом `search`. Дубль в своей организации → `409 code:"already_taken"` + существующий заказ. Груза нет → `404`, снят/неактуален → `410`. Общая база не меняется. `fetchContacts: true` — единственная причина сходить в живой ATI (контакты фирмы). Пишет аудит `order_take_from_base`. |
| `GET /api/orders/:id/negotiation` | Лента согласования + сводка по заказу (цена, согласованная цена, состояние переговоров, когда вернуться). |
| `POST /api/orders/:id/negotiation` | Добавить запись: `{ kind, text?, priceOffer? }`, только `note/price_offer/call/email/document`. Для `price_offer` сумма обязательна. Автоматические виды → `400`. Чужой заказ → `404`. |
| `PATCH /api/orders/:id` | Расширен: `status` (канон + легас, переходы проверяются), `agreedPrice`, `negotiationStatus`, `nextFollowUpAt`. Запрещённый переход → `400 code:"invalid_status_transition"` + `allowed[]`. Смена цены/статуса автоматически пишется в ленту. Итог переговоров переводит заказ сам: `agreed` → «Согласован», `lost` → «Отклонён». |
| `GET /api/ati/sandbox` | Песочница: **настоящие заказы** организации (`routeId = null`, не закрытые) в прежней форме ответа + поля процесса (`stage`, `status`, `statusLabel`, `agreedPrice`, `negotiationStatus`, `nextFollowUpAt`, `atiCacheId`, `orderId`). |
| `DELETE /api/ati/sandbox` | Вернуть груз в базу: удаляет **свой** заказ (скоупленный `deleteMany`). Заказ в рейсе → `409`; закрыт → `409`; создан вручную (не из базы) → `400 code:"not_from_cache"`. Пишет аудит `order_return_to_base`. |
| `POST /api/routes` | Сборка рейса: `orderIds[]` — привязать существующие согласованные заказы (основной путь), `orders[]` — прежний путь песочницы (создаёт заказы). `vehicleId` **не обязателен**. Несогласованные → `409 code:"orders_not_agreed"`; уже в другом рейсе → `409 code:"orders_already_in_route"`; чужие → `404`. |
| `POST /api/ati/import` | Совместимый вход: делегирует в `from-cache` (прежняя логика помечала общую базу и заказ не создавала). Функция `importAtiLoadToOrder` удалена. |
| `GET /api/routes/[routeId]/map` | Линия рейса: сегменты по заказам (`geometry` из OSRM, `colorIndex`, км, статус), рамка `bounds` и `problems` — города без координат. Чужой рейс → `404`. |
| `GET/POST /api/ati/cron` | Сканы **по расписанию**: профили `AtiScanConfig` решают, что и как часто сканировать (города, радиус, минимальный вес, типы кузова, интервал). Закрыт `CRON_SECRET` (без переменной — 503) или сессией сотрудника. |
| `GET /api/sidebar-counts` | Счётчики меню: `orders` — заказы, ждущие действия логиста (Поиск/Согласование или просроченное напоминание), `chat` — непрочитанные сообщения организации (кроме собственных). |

Статистика базы (`getAtiStats`): «Взято» теперь считается по заказам
(`Order.atiCacheId`), а не по метке в общей таблице.

## 5. Экраны

**Карточка заказа — и страница, и панель** (решение пользователя: «и то, и
другое»). Контент один и тот же — `components/orders/order-process.tsx`:

- **`/orders/[id]`** — полная страница: степпер этапов (Поиск → Согласование →
  Маршрут → Документы → Назначение → Контроль), сводка (клиент, телефон, цена,
  согласованная цена, переговоры, когда вернуться, срок погрузки, рейс,
  источник), блок согласования и торга, лента записей;
- **выдвижная панель в песочнице** (`Sheet` справа) — те же данные для быстрых
  действий, контекст холста не теряется. Открывается иконкой «Согласование» у
  груза в списке слева или кнопкой «Согласование» в форме редактирования
  элемента холста; оттуда же — ссылка «Открыть полную карточку заказа».

Что можно сделать в карточке:

- «Договорились» — согласованная цена + состояние переговоров `agreed` (заказ
  сам переходит в «Согласован»);
- «Сохранить цену и срок» — `agreedPrice` и `nextFollowUpAt` без смены статуса;
- «Не договорились» — `lost`, заказ отклоняется (подтверждение через
  AlertDialog, `window.confirm` не используется);
- «Перевести на этап» — список только тех статусов, которые разрешает канон
  переходов;
- «Вернуть в базу» — только для заказа из базы ATI и пока он не в рейсе;
- добавить запись в ленту: заметка, предложение цены, звонок, письмо, документ.
  Записи «Изменение цены» и «Смена статуса» добавляет сервер — вручную их
  создать нельзя (API отвечает 400).

Звонков и писем клиенту система сама не делает — в карточке это написано явно.

**Песочница (`/orders`, вкладка «Мои заказы»)** — ядро сохранено, холст и
перетаскивание работают как раньше. Изменилось:

- в списке слева — настоящие заказы организации, у каждого бейдж этапа
  («В поиске», «Согласование», «Согласован», …);
- на холст берутся **только согласованные** заказы: на несогласованном клик даёт
  подсказку «Заказ ещё не согласован», а попытка оформить рейс — понятную ошибку
  `orders_not_agreed`;
- при оформлении рейса заказы передаются по `orderIds` — дубли не создаются;
- в форме элемента холста — «Этап заказа» вместо прежнего «Статус в песочнице»
  и кнопки «Согласование» / «Полная карточка».

**Поиск грузов — отдельная страница `/search`** (решение пользователя:
«отдельная страница», максимум места для фильтров и таблицы). В `/orders`
вкладка «ATI.SU Поиск» убрана, вместо неё кнопка **«Найти груз»** в шапке; пункт
«Поиск грузов» добавлен в сайдбар.

На странице поиска:

- **вкладка «Своя база» — первая и по умолчанию**: это накопленная база, которую
  наполняют плановые сканы, поиск по ней мгновенный;
- **вкладка «Живой поиск ATI» — явная вторая опция** с предупреждением, что
  запрос уходит на ati.su и тратит лимиты токена;
- кнопка «Взять» стала «Взять в работу»: создаёт заказ организации на этапе
  «Поиск», груз **остаётся в общей базе** (его могут взять другие организации) и
  помечается у нас как «В работе».

**Один рейс — одна линия с цветными сегментами по заказам** (F3). В карточке
рейса (`/routes`) в развёрнутом виде есть блок «Маршрут на карте»: карта
открывается кнопкой «Показать карту» и только тогда запрашивает данные
(`GET /api/routes/[routeId]/map`), потому что за ней стоят внешние сервисы —
Nominatim (координаты городов) и OSRM (дорога). Каждый заказ рейса — свой цвет,
нумерованная точка и всплывающая подсказка со ссылкой на карточку заказа;
легенда под картой повторяет цвета.

Что важно в поведении карты:

- координаты городов кэшируются в таблице `GeoCache` (общий справочник), поэтому
  второй показ карты не идёт в сеть; запросы к Nominatim идут по одному с паузой
  (правила сервиса — не чаще 1 раза в секунду);
- если OSRM недоступен, сегмент рисуется **прямой и пунктиром**, а под картой
  появляется пояснение: дорогу получить не удалось;
- город, координаты которого определить не удалось, **не выдумывается**: под
  картой появляется список таких городов с подсказкой проверить название;
- геометрия спрашивается на сервере (в браузер летит готовый набор сегментов),
  поэтому лимиты внешних сервисов не тратятся на каждого пользователя.

**«Заказ из текста»** (вкладка на `/orders`, раньше — «AI импорт» с
имитацией ИИ). Теперь это честный разбор: текст заявки разбирается
**правилами** (регулярные выражения, без внешних сервисов), поля показываются
рядом с текстом и их можно поправить руками, а чего в тексте не нашлось — видно
списком предупреждений («город не найден», «цена не найдена»). Заказ создаётся
**только по явной кнопке «Создать заказ»** и сразу открывается его карточка;
статус — «Согласование», потому что цена ещё не согласована.

Подписи канонических этапов показывают: карточка процесса заказа
(`components/orders/order-process.tsx` — на странице `/orders/[id]` и в песочнице),
лента песочницы (`orders-sandbox.tsx`), карточка активного рейса
(`components/routes/active-route-card.tsx`) и мобильный контур водителя
(`app/m/**`). Прежние значения статусов оставлены псевдонимами
(`LEGACY_ORDER_STATUS_MAP`), чтобы старые строки в базе отображались верно.

## 6. ⚠️ Миграция: порядок действий на вашей машине

В песочнице Arena нет движков Prisma, поэтому `prisma generate` / `db push` и
сам перенос данных выполняете вы. **До `--apply` скрипт ничего не пишет.**

```bash
cd <папка-проекта>

# 0) Резервная копия базы
cp prisma/dev.db ~/loginex-backup/dev.db-$(date +%F-%H%M)

# 1) Обновление кода
git fetch origin
git checkout arena/01a0c0e1-repo
git pull origin arena/01a0c0e1-repo

# 2) Схема: новые колонки Order + таблица OrderNegotiation
npm run db:generate
npm run db:push

# 3) СУХОЙ ПРОГОН — посмотреть, что изменится (база не трогается)
npm run db:migrate-order-stages

# 4) Применить перенос (только если сухой прогон выглядит правильно)
npm run db:migrate-order-stages -- --apply

# 5) Контрольный сухой прогон — должно быть «переносить нечего»
npm run db:migrate-order-stages
```

Что делает скрипт:

1. приводит прежние статусы к канону (`new → search`, `confirmed → agreed`,
   `in_transit/loading/unloading → control`, `completed → delivered`, …);
2. проставляет `negotiationStatus` там, где он очевиден из этапа
   (согласованные и дальше → `agreed`, отклонённые → `lost`, идущее
   согласование → `in_progress`);
3. восстанавливает `Order.atiCacheId` по `sourceId` — только если строка базы
   существует и в этой организации нет другого заказа на ту же строку;
4. сообщает о неизвестных значениях статуса — такие строки **не меняются**, их
   нужно разобрать вручную.

`agreedPrice` скрипт **не выдумывает**: сумма остаётся пустой, пока её не укажет
логист. Записи в ленту согласования скрипт не создаёт (это перенос данных, а не
событие переговоров).

Если база уже PostgreSQL — тот же порядок, только вместо `db:push` используйте
свой способ применения схемы (`npm run schema:postgres` и `db push` по
`prisma/schema.postgres.prisma`).

## 7. Ручная проверка в браузере (после миграции)

1. `/orders` → «База» → «Взять в работу» на любом грузе: появляется тост, груз
   помечается «В работе», в базе остаётся.
2. `/orders` → «Песочница»: взятый груз виден в списке слева с бейджем
   «В поиске».
3. Клик по несогласованному грузу → подсказка «Заказ ещё не согласован», на холст
   не падает.
4. `PATCH`-проверка через карточку заказа (или API): поставить
   `negotiationStatus: "agreed"` → статус становится «Согласован», в ленте
   появляется запись «Смена статуса».
5. Песочница: согласованный груз перетаскивается на холст → «Оформить рейс» →
   рейс создан, заказ получил статус «В рейсе».
6. Рейс без машины: `POST /api/routes` с `orderIds` и без `vehicleId` → `200`,
   `route.vehicleId = null`.
7. Чужая организация (второй аккаунт): тот же груз из базы берётся отдельно,
   заказы и ленты не пересекаются.
8. «Вернуть в базу» (крестик в списке песочницы): заказ удаляется, строка базы
   остаётся, в журнале аудита появляется `order_return_to_base`.
9. Карточка заказа: иконка «Согласование» у груза в списке песочницы → панель
   справа; «Договорились» с суммой → бейдж этапа становится «Согласован», в ленте
   появляются записи «Изменение цены» и «Смена статуса» с пометкой
   «автоматически»; «Перевести на этап» предлагает только разрешённые статусы.
10. `/orders/[id]` (ссылка «Открыть полную карточку заказа») — те же данные на
    отдельной странице, кнопка «назад» возвращает в `/orders`.
11. `/search` (кнопка «Найти груз» или пункт сайдбара): первая вкладка — «Своя
    база», вкладка «Живой поиск ATI» открывается с предупреждением.
12. `/routes` → развернуть рейс → «Показать карту»: линия рейса разбита на
    цветные сегменты по заказам, у каждой точки номер и ссылка на карточку
